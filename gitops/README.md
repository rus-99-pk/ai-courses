# Как должен выглядеть курс по GitOps по мнению AI 

---

**Цель курса:** Изучить методологию GitOps и освоить инструменты для ее реализации, научиться управлять инфраструктурой и приложениями в Kubernetes, используя Git как единый источник истины.

**Предварительные требования:** Базовое понимание работы с командной строкой, Docker (концептуально), и опыт работы с Git.

---

**Модуль 1: Основы Kubernetes**

*   **Цель модуля:** Получить необходимые базовые знания о ключевых компонентах Kubernetes, их декларативном управлении и сетевых аспектах для дальнейшего применения GitOps.
*   **Тема 1: Введение в Kubernetes. Основные понятия и архитектура**
    *   **Теория:** Что такое Kubernetes, зачем он нужен. Декларативный vs Императивный подход. Архитектура кластера (Control Plane, Worker Nodes). Ключевые компоненты Control Plane (kube-apiserver, etcd, kube-scheduler, kube-controller-manager, cloud-controller-manager). Ключевые компоненты Worker Node (kubelet, kube-proxy, Container Runtime). Namespaces. kubectl - основной инструмент взаимодействия.
    *   **ДЗ:** Нет. (Эта тема вводная, фокусируемся на понимании).
*   **Тема 2: Объекты в Kubernetes**
    *   **Теория:** Подробное изучение ключевых объектов: Pods (жизненный цикл), Deployments (управление ReplicaSets, стратегии обновления - Rolling Update, Recreate), Services (типы: ClusterIP, NodePort, LoadBalancer, ExternalName). YAML-манифесты для описания объектов. Селекторы и лейблы.
    *   **ДЗ:** Развертывание простого приложения.
        *   **Задача:** Написать YAML-манифесты для:
            *   Deployment, запускающего 3 реплики простого веб-приложения (например, Nginx или `k8s.gcr.io/echoserver:1.10`).
            *   Service типа ClusterIP для доступа к этому Deployment.
            *   Service типа NodePort для внешнего доступа к этому Deployment (или LoadBalancer, если работаете в облаке).
        *   **Измеряемость:**
            1.  Предоставьте YAML-файлы манифестов.
            2.  Примените манифесты к кластеру (`kubectl apply -f <файл>`).
            3.  Предоставьте вывод команд `kubectl get pods`, `kubectl get deploy`, `kubectl get svc`.
            4.  Продемонстрируйте доступность приложения: `curl <IP:NodePort>` или доступ через LoadBalancer IP.
*   **Тема 3: Сетевая подсистема в Kubernetes**
    *   **Теория:** Модель сети Kubernetes (каждый под имеет свой IP). Взаимодействие Pod-to-Pod, Pod-to-Service. Роль kube-proxy. CNI (Container Network Interface) - концепция и примеры (Calico, Flannel). Введение в Ingress (контроллеры Ingress, Ingress-ресурсы) как способ управления внешним доступом с учетом правил маршрутизации по доменному имени/пути.
    *   **ДЗ:** Настройка сетевого взаимодействия и внешнего доступа через Ingress.
        *   **Задача:**
            *   Развернуть два различных приложения (например, frontend и backend).
            *   Настроить Service ClusterIP для backend и продемонстрировать доступ frontend к backend по имени Service.
            *   Установить Ingress-контроллер (например, Nginx Ingress Controller, если его нет в кластере).
            *   Написать Ingress-ресурс для доступа к frontend по определенному URL (например, `/app`).
        *   **Измеряемость:**
            1.  Предоставьте YAML-файлы для Deployment и Service обоих приложений, а также Ingress-ресурса.
            2.  Предоставьте вывод команд `kubectl get pods`, `kubectl get svc`, `kubectl get ingress`.
            3.  Продемонстрируйте успешный curl с пода frontend на Service backend.
            4.  Продемонстрируйте успешный внешний доступ к frontend через IP Ingress-контроллера и настроенный путь (например, `curl http://<Ingress-IP>/app`).
*   **Тема 4: Хранение данных в Kubernetes**
    *   **Теория:** Проблема эфемерности данных подов. Понятие Volume. Типы Volume (emptyDir, hostPath, анонс CSI). PersistentVolumes (PV) и PersistentVolumeClaims (PVC). StorageClasses как способ динамического выделения PV. Привязка PVC к поду. Жизненный цикл PV/PVC.
    *   **ДЗ:** Использование постоянного хранилища.
        *   **Задача:**
            *   Написать YAML-манифесты для PersistentVolumeClaim (PVC).
            *   Написать Deployment для приложения, которое сохраняет данные на Volume (например, простой веб-сервер, пишущий логи в файл, или база данных вроде SQLite).
            *   Подключить PVC к поду через VolumeMounts.
            *   Удалить под и убедиться, что новый под (созданный Deployment-ом) имеет доступ к тем же данным.
        *   **Измеряемость:**
            1.  Предоставьте YAML-файлы для PVC и Deployment.
            2.  Предоставьте вывод команд `kubectl get pvc`.
            3.  Продемонстрируйте сохранение данных: например, запишите файл из одного пода (`kubectl exec <pod-name> -- sh -c 'echo "test" > /path/to/volume/test.txt'`), затем удалите этот под (`kubectl delete pod <pod-name>`). После создания нового пода Deployment-ом, проверьте наличие файла (`kubectl exec <new-pod-name> -- cat /path/to/volume/test.txt`).
            *   *Примечание:* Для этого ДЗ потребуется настроенный StorageClass в кластере или ручное создание PV. Для простоты локально можно использовать `hostPath` PV/StorageClass.
*   **Тема 5: Requests, limits и load balancing в Kubernetes**
    *   **Теория:** Управление ресурсами (CPU, Memory) для контейнеров через `requests` и `limits`. Quality of Service (QoS) классов (Guaranteed, Burstable, BestEffort). Балансировка нагрузки в Service ClusterIP/NodePort/LoadBalancer. Введение в Horizontal Pod Autoscaler (HPA) - автоматическое масштабирование подов по метрикам (CPU, Memory, кастомные).
    *   **ДЗ:** Нет. (Теория важна для понимания надежности, но сложно измерить без инструментов мониторинга и генерации нагрузки).
*   **Тема 6: Архитектурный подход Service Mesh**
    *   **Теория:** Что такое Service Mesh (Istio, Linkerd). Зачем нужен: обнаружение сервисов, трафик-менеджмент (A/B тестирование, канареечные релизы), безопасность (mTLS), наблюдаемость (метрики, логи, трассировка). Sidecar-контейнеры. Место Service Mesh в архитектуре микросервисов.
    *   **ДЗ:** Нет. (Вводная тема, сложно реализовать в рамках базового курса).
*   **Тема 7: Развертывание кластера Kubernetes**
    *   **Теория:** Обзор методов развертывания: локальные (Minikube, Kind, Docker Desktop), self-managed (kubeadm, kops, Kubespray), cloud-managed (GKE, EKS, AKS). Плюсы и минусы каждого подхода. Фокус на одном простом методе для локальной разработки/тестирования (например, Kind или Minikube).
    *   **ДЗ:** Установка локального кластера Kubernetes.
        *   **Задача:** Используя инструмент Kind или Minikube, развернуть локальный кластер Kubernetes на своей машине.
        *   **Измеряемость:**
            1.  Предоставьте шаги, которые вы выполнили для установки инструмента и развертывания кластера.
            2.  Предоставьте вывод команды `kubectl cluster-info`.
            3.  Предоставьте вывод команды `kubectl get nodes`.
            4.  Убедитесь, что вы можете взаимодействовать с кластером с помощью `kubectl`.

**Модуль 2: Введение в методологию GitOps**

*   **Цель модуля:** Понять основные принципы GitOps, его преимущества и связь с Git и CI/CD.
*   **Тема 1: Основы Git. Использование CI/CD в Git проектах**
    *   **Теория:** Краткий обзор Git: коммиты, ветки, слияния, Pull Requests (Merge Requests). Концепция CI/CD (Continuous Integration, Continuous Delivery/Deployment). Роль CI в сборке и тестировании кода/образов. Роль CD в доставке изменений. Разница между Push- и Pull-based CD.
    *   **ДЗ:** Нет. (Вводная/повторяющая тема).
*   **Тема 2: Введение в GitOps**
    *   **Теория:** Определение GitOps. Ключевые принципы:
        1.  Система, управляемая декларативно.
        2.  Состояние системы версионируется в Git.
        3.  Автоматическое применение одобренных изменений из Git.
        4.  Использование программных агентов для обеспечения правильности состояния и его самовосстановления.
        Преимущества GitOps: скорость, надежность, безопасность (меньше ручных операций), аудит, воспроизводимость, упрощение отката.
        Сравнение GitOps с традиционным Push-based CD.
    *   **ДЗ:** Нет. (Концептуальная тема).
*   **Тема 3: Управление конфигурацией с помощью Git**
    *   **Теория:** Как хранить декларативные манифесты Kubernetes в Git. Структура Git-репозитория для конфигурации. Разделение конфигурации по средам (dev, staging, prod) или приложениям. Использование веток или директорий для управления изменениями и средами. Подготовка к автоматизированному применению.
    *   **ДЗ:** Создание репозитория конфигурации.
        *   **Задача:**
            *   Создать новый Git-репозиторий (на GitHub, GitLab, Bitbucket или локально).
            *   В этом репозитории создать структуру директорий для хранения манифестов (например, `/kubernetes/apps/myapp`, `/kubernetes/environments/dev`).
            *   Поместить в одну из этих директорий YAML-манифесты простого приложения из ДЗ Модуля 1 (Deployment, Service).
            *   Изменить какой-либо параметр в Deployment (например, количество реплик) в Git и вручную применить изменение к кластеру из локальной копии репозитория.
        *   **Измеряемость:**
            1.  Предоставьте ссылку на Git-репозиторий.
            2.  Покажите структуру директорий в репозитории.
            3.  Предоставьте коммит, где вы изменили манифест.
            4.  Предоставьте вывод команд `kubectl apply -f <путь_к_манифесту_в_репо>` и `kubectl get deploy` после применения изменения, демонстрирующий, что изменение (например, количество реплик) было успешно применено.

**Модуль 3: Инструменты GitOps**

*   **Цель модуля:** Изучить основные инструменты для реализации GitOps (Argo CD, Flux), понять их работу и научиться их использовать для синхронизации состояния кластера с Git.
*   **Тема 1: Инструментарий и подходы для реализации GitOps**
    *   **Теория:** Введение в Argo CD и Flux CD как ведущие инструменты. Архитектура Pull-based агентов. Как они работают: мониторинг Git-репозитория, сравнение желаемого состояния (Git) с фактическим состоянием кластера, применение изменений. Основные ресурсы инструментов (Application в Argo CD, GitRepository/Kustomization/HelmRelease в Flux).
    *   **ДЗ:** Нет. (Обзорная тема).
*   **Тема 2: Использование паттерна App of Apps (с Argo CD)**
    *   **Теория:** Управление множеством приложений и их взаимосвязями. Паттерн App of Apps в Argo CD: создание корневого Application-ресурса, который ссылается на другие Application-ресурсы в Git. Организация репозитория для App of Apps. Преимущества: централизованное управление, модульность.
    *   **ДЗ:** Развертывание нескольких приложений с помощью App of Apps.
        *   **Задача:**
            *   Установить Argo CD в ваш локальный кластер (ДЗ Модуля 1, Тема 7).
            *   Создать Git-репозиторий со структурой, подходящей для App of Apps (например, корневая папка с `root.yaml`, и подпапки `/apps/app1`, `/apps/app2` с их манифестами и `Application`-ресурсами для Argo CD).
            *   Поместить манифесты двух разных простых приложений в `/apps/app1` и `/apps/app2`.
            *   Создать `Application`-ресурсы для каждого приложения в соответствующих папках, указывающие на их манифесты.
            *   Создать корневой `Application`-ресурс (`root.yaml`), указывающий на директории `/apps/app1` и `/apps/app2`.
            *   Настроить Argo CD для синхронизации корневого `Application`-ресурса.
            *   Продемонстрировать, что Argo CD автоматически развернул оба дочерних приложения.
        *   **Измеряемость:**
            1.  Предоставьте ссылку на Git-репозиторий с настроенной структурой App of Apps.
            2.  Предоставьте вывод команды `kubectl get applications -n argocd` (или неймспейс, куда установлен Argo CD).
            3.  Предоставьте скриншоты веб-интерфейса Argo CD, демонстрирующие корневое Application и дочерние Application в статусе `Healthy` и `Synced`.
*   **Тема 3: Применение ApplicationSet (с Argo CD)**
    *   **Теория:** ApplicationSet как расширение App of Apps для автоматического создания Application-ресурсов на основе различных генераторов (Git-директории, кластеры, параметры). Примеры использования ApplicationSet для развертывания одного и того же набора приложений в нескольких кластерах или для всех директорий в определенной папке Git.
    *   **ДЗ:** Нет. (Эта тема углубляет понимание Argo CD, сложно измерить без более комплексной инфраструктуры).
*   **Тема 4: Интеграция инструмента Flux**
    *   **Теория:** Установка и настройка Flux CD. Ключевые ресурсы Flux: `GitRepository` (указывает на репозиторий), `Kustomization` (применяет Kustomize-конфигурации из репо), `HelmRelease` (деплоит Helm-чарты из репо). Способы синхронизации. Самовосстановление и обнаружение дрифта.
    *   **ДЗ:** Синхронизация приложения с помощью Flux.
        *   **Задача:**
            *   Установить Flux CD в ваш локальный кластер.
            *   Создать Git-репозиторий с манифестами простого приложения (аналогично ДЗ Модуля 2, Тема 3).
            *   Настроить Flux CD для синхронизации этого репозитория, создав ресурсы `GitRepository` и `Kustomization` (или `HelmRelease`, если вы используете Helm-чарт).
            *   Изменить манифест приложения в Git (например, сменить версию образа или количество реплик).
            *   Продемонстрировать, что Flux автоматически применил эти изменения в кластере без ручного вмешательства.
        *   **Измеряемость:**
            1.  Предоставьте ссылку на Git-репозиторий.
            2.  Предоставьте YAML-файлы ресурсов Flux (`GitRepository`, `Kustomization`/`HelmRelease`).
            3.  Предоставьте вывод команд `kubectl get gitrepositories -n flux-system` и `kubectl get kustomizations -n flux-system` (или `helmreleases`).
            4.  Предоставьте коммит в Git, где вы изменили манифест приложения.
            5.  Предоставьте вывод команды `kubectl get deploy <имя_деплоймента>` после того, как Flux применит изменение, демонстрирующий, что изменение (например, новая версия образа или количество реплик) было успешно применено.

**Модуль 4: Развертывание инфраструктуры GitOps**

*   **Цель модуля:** Расширить принципы GitOps на управление инфраструктурой, включая облачные ресурсы, используя соответствующие инструменты.
*   **Тема 1: Применение инфраструктуры с помощью Terraform в GitOps**
    *   **Теория:** Управление инфраструктурой как кодом (IaC) с помощью Terraform. Хранение `.tf` файлов и state-файла (удаленно, например, в S3/GCS/Azure Blob или Terraform Cloud) в связке с Git. Интеграция Terraform в GitOps flow:
        *   Подход 1: CI-пайплайн, который при изменениях в `.tf` файлах в Git запускает `terraform plan` (в PR) и `terraform apply` (после мерджа в основную ветку). Это "Push-based GitOps".
        *   Подход 2: Использование Kubernetes-операторов (например, Flux's Terraform Controller или Argo CD со специализированным контроллером), которые мониторят `.tf` файлы в Git и применяют Terraform изнутри кластера. Это "Pull-based GitOps" для Terraform.
    *   **ДЗ:** Управление простым ресурсом с помощью Terraform через Git.
        *   **Задача:**
            *   Выбрать простой облачный ресурс для управления (например, S3 bucket в AWS, Resource Group в Azure, GCS bucket в GCP) или использовать локальный провайдер Terraform (например, `null_resource` или `local_file`).
            *   Написать Terraform-код (`.tf` файлы) для создания этого ресурса.
            *   Создать Git-репозиторий для инфраструктурного кода.
            *   Настроить автоматический запуск Terraform при изменениях в Git. Это может быть простой скрипт, который вы запустите локально после пуша, или (предпочтительно) настроить базовый CI-пайплайн (GitHub Actions, GitLab CI, Jenkins), который выполняет `terraform init`, `terraform plan`, `terraform apply` при пуше в основную ветку.
        *   **Измеряемость:**
            1.  Предоставьте ссылку на Git-репозиторий с Terraform-кодом.
            2.  Предоставьте `.tf` файлы.
            3.  Опишите, как настроена автоматизация (скрипт или конфигурация CI).
            4.  Продемонстрируйте, что изменение параметра ресурса в Git и пуш в репозиторий привел к успешному изменению ресурса в облаке (или локально). Предоставьте логи выполнения скрипта/пайплайна и скриншот/вывод команды, подтверждающий изменение ресурса.
            *   *Примечание:* Настройка облачных провайдеров и CI требует аккаунта в облаке и CI-системе. Для локального выполнения можно использовать `local-exec` или `local_file` ресурс в Terraform и скрипт, запускаемый локально после коммита.
*   **Тема 2: Использование инструмента Crossplane**
    *   **Теория:** Управление внешними ресурсами через K8s API. Установка Crossplane и провайдеров (AWS, GCP, Azure, vSphere и др.). Понятие Composite Resources (XRs) и Compositions для абстракции инфраструктуры. Использование Crossplane CRD для описания желаемого состояния внешних ресурсов в YAML. Интеграция Crossplane с GitOps инструментами (Argo CD, Flux).
    *   **ДЗ:** Управление облачным ресурсом через Crossplane и GitOps.
        *   **Задача:**
            *   Установить Crossplane в ваш кластер Kubernetes.
            *   Установить провайдер для вашей облачной платформы (или использовать `provider-kubernetes`).
            *   Настроить учетные данные провайдера как Secret в Kubernetes.
            *   Написать YAML-манифест для создания простого облачного ресурса с помощью Crossplane CRD (например, S3Bucket, PostgreSQLInstance, ServiceAccount).
            *   Поместить этот YAML-манифест в ваш GitOps-репозиторий, который синхронизируется Argo CD или Flux (например, в отдельную директорию `infra/crossplane`).
            *   Настроить ваш GitOps инструмент для синхронизации этой директории.
            *   Продемонстрировать, что ресурс был создан в облаке (или в кластере, если используете `provider-kubernetes`).
        *   **Измеряемость:**
            1.  Предоставьте ссылку на Git-репозиторий с Crossplane YAML.
            2.  Предоставьте YAML-файл ресурса Crossplane.
            3.  Предоставьте вывод команд `kubectl get <тип_вашего_crossplane_ресурса>` (например, `kubectl get s3buckets`).
            4.  Предоставьте скриншот или вывод команды из консоли облачного провайдера, подтверждающий создание ресурса.
*   **Тема 3: Автоматизация тестирования инфраструктуры**
    *   **Теория:** Зачем тестировать инфраструктурный код? Методы тестирования: статический анализ (linting, `terraform validate`), модульные тесты (Terratest, InSpec), интеграционные тесты. Тестирование Kubernetes-манифестов (`kubeconform`, `kubeval`, OPA/Gatekeeper политики). Интеграция тестов в CI/CD/GitOps пайплайн.
    *   **ДЗ:** Нет. (Вводная тема про практики).
*   **Тема 4: Мониторинг с помощью GitOps**
    *   **Теория:** Управление конфигурацией мониторинга (PrometheusRules, ServiceMonitors, Grafana Dashboards) через GitOps. Хранение YAML-файлов конфигурации мониторинга в Git и синхронизация их с кластером с помощью GitOps инструмента. Пример: Prometheus Operator, Grafana Operator.
    *   **ДЗ:** Нет. (Требует развернутой системы мониторинга).
*   **Тема 5: Интеграция CI/CD и GitOps**
    *   **Теория:** Подробное рассмотрение взаимодействия CI и GitOps. CI собирает артефакты (образы Docker, Helm-чарты). После успешной сборки и тестирования CI обновляет манифесты в GitOps репозитории, указывая на новую версию артефакта. Этот коммит триггерит GitOps инструмент для деплоя. Примеры: Webhooks, Argo CD Image Updater, Flux Image Automation.
    *   **ДЗ:** Нет. (Концептуальная тема, подводящая к финальному проекту).
*   **Тема 6: Деплой приложений с помощью GitOps**
    *   **Теория:** Повторение и закрепление процесса деплоя приложений: изменение манифеста в Git -> GitOps инструмент видит изменение -> GitOps инструмент применяет изменение в кластере. Стратегии обновления (Rolling Update, Canary, Blue/Green) через GitOps (с помощью Deployment-стратегий, Service Mesh или специализированных инструментов вроде Argo Rollouts).
    *   **ДЗ:** Обновление версии приложения через GitOps.
        *   **Задача:**

            1.  Предоставьте ссылку на Git-репозиторий и коммит с изменением тега образа.

**Модуль 5: Проектная работа**

*   **Цель модуля:** Применить все полученные знания для реализации комплексного сценария управления инфраструктурой и приложениями с помощью GitOps.
*   **Задача:** Развернуть и управлять полноценным веб-приложением с backend и базой данных, используя GitOps.
*   **Сценарий:** Вам необходимо развернуть "гостевую книгу" - простое веб-приложение, состоящее из:
    1.  **Backend API:** Принимает и отдает записи гостевой книги. Хранит данные в базе данных.
    2.  **Frontend:** Простая веб-страница, которая взаимодействует с Backend API для отображения и добавления записей.
    3.  **База данных:** PostgreSQL для хранения записей.
*   **Требования к реализации GitOps:**
    *   Вся конфигурация (манифесты приложений, конфигурация базы данных) должна храниться в одном или нескольких Git-репозиториях.
    *   Управление жизненным циклом базы данных (создание, обновление) должно осуществляться через Infrastructure as Code (IaC) с помощью GitOps. Выберите **Crossplane** для управления базой данных из Kubernetes.
    *   Развертывание и обновление Frontend и Backend должно осуществляться с помощью одного из GitOps инструментов: **Argo CD или Flux CD**.
    *   Должен быть настроен внешний доступ к Frontend.
    *   Продемонстрируйте процесс обновления версии Backend или Frontend через изменение тега образа в Git и автоматический деплой с помощью GitOps инструмента.
    *   Убедитесь, что приложение после развертывания успешно работает (Frontend общается с Backend, Backend общается с БД).

*   **Измеряемость (Результаты проектной работы):**
    1.  **Git-репозиторий:** Предоставьте ссылку на ваш Git-репозиторий, содержащий:
        *   Манифесты Kubernetes для Frontend и Backend (Deployment, Service, Ingress).
        *   YAML-манифесты Crossplane для создания инстанса базы данных PostgreSQL (или другого типа БД, который поддерживает ваш провайдер Crossplane).
        *   YAML-манифесты для настройки Argo CD/Flux (Application/AppSet или GitRepository/Kustomization/HelmRelease), указывающие на ваши манифесты приложений и Crossplane.
        *   (Опционально) Скрипты или конфигурация для сборки образов приложений (достаточно концепции или просто использовать готовые образы).
    2.  **Работающий кластер:** Убедитесь, что ваш локальный (или облачный, если вы его используете) кластер Kubernetes запущен.
    3.  **Установленные инструменты:** Продемонстрируйте, что Argo CD/Flux и Crossplane установлены и настроены в кластере (`kubectl get pods -n <неймспейсы инструментов>`).
    4.  **Развернутая инфраструктура:** Продемонстрируйте, что инстанс базы данных успешно создан через Crossplane (`kubectl get <ваш_тип_crossplane_бд_ресурса>` и скриншот/вывод из консоли облака/БД).
    5.  **Развернутое приложение:** Продемонстрируйте, что Frontend и Backend успешно развернуты и запущены (`kubectl get pods`, `kubectl get svc`, `kubectl get ingress`).
    6.  **Функциональность приложения:** Продемонстрируйте, что гостевая книга работает: откройте Frontend в браузере, добавьте запись, убедитесь, что она появилась и сохраняется после перезапуска подов приложения.
    7.  **Процесс обновления:** Запишите короткое видео или сделайте серию скриншотов, показывающих:
        *   Изменение тега образа Frontend или Backend в Git-репозитории.
        *   Коммит и пуш изменения.
        *   Argo CD/Flux обнаруживает изменение и начинает синхронизацию.
        *   Kubernetes обновляет поды Deployment.
        *   Приложение доступно по тому же адресу, но показывает новую версию.

Этот проект позволит связать воедино все темы курса: от базовых объектов K8s и управления ими декларативно, через принципы GitOps и выбор инструментов, до управления как приложениями, так и инфраструктурой из единого источника истины - Git-репозитория, с автоматической синхронизацией.
