# Тема 3: Управление состоянием (State Management)

## Какую проблему мы решаем?

До сих пор мы работали в одиночку, и файл `terraform.tfstate` лежал в нашей локальной папке. Теперь представьте, что вы работаете в команде.

**Проблемы с локальным состоянием:**
1.  **Конфликты**: Если два инженера одновременно запустят `terraform apply`, они могут попытаться изменить один и тот же ресурс, что приведет к непредсказуемым последствиям. Последний применивший изменения "победит", затерев работу коллеги.
2.  **Потеря состояния**: Если вы удалите папку проекта или ваш жесткий диск выйдет из строя, вы потеряете файл `.tfstate`. Terraform больше не будет "знать" о созданной инфраструктуре, и управлять ею станет невозможно.
3.  **Небезопасно**: В файле состояния могут храниться чувствительные данные (например, пароли от баз данных), и хранить их в Git-репозитории — плохая практика.

## Решение: Удаленное состояние (Remote State)

Решение — хранить файл состояния в удаленном, общем и безопасном месте. Это называется **"backend"** (бэкенд).

**Преимущества удаленного состояния:**
-   **Совместная работа**: Вся команда работает с единым, актуальным состоянием.
-   **Блокировка состояния (State Locking)**: Перед выполнением `apply` Terraform "заблокирует" файл состояния. Если другой инженер в это время попытается запустить `apply`, он получит ошибку и будет ждать, пока первая операция не завершится. Это предотвращает конфликты.
-   **Безопасность и надежность**: Хранение в надежных хранилищах (как AWS S3) с версионированием и шифрованием.

### Задача: Перенести наше локальное состояние в удаленный бэкенд на AWS S3 с блокировкой через DynamoDB.

**Почему S3 + DynamoDB?**
-   **AWS S3**: Надежное, дешевое и популярное объектное хранилище. Идеально для хранения `tfstate` файла.
-   **AWS DynamoDB**: Быстрая NoSQL база данных, которую Terraform использует для механизма блокировок. Когда кто-то запускает `apply`, Terraform создает запись в таблице DynamoDB. Если кто-то еще пытается это сделать, Terraform видит запись и ждет.

## Шаг 1: Создание S3 бакета и таблицы DynamoDB

Эти ресурсы для хранения состояния нужно создать *до того*, как мы настроим бэкенд. Их можно создать вручную через консоль AWS или с помощью отдельной, простой Terraform-конфигурации.

**Действия (выполните один раз для команды):**
1.  **Создайте S3 бакет** в AWS. Имя бакета должно быть **глобально уникальным**. Например: `my-awesome-project-tfstate-2023`. Включите версионирование (Versioning) для бакета — это хорошая практика для защиты от случайного удаления.
2.  **Создайте таблицу DynamoDB**.
    -   Имя таблицы: например, `terraform-state-locks`.
    -   Первичный ключ (Primary Key): `LockID` (тип: String).
    -   Остальные настройки можно оставить по умолчанию.

## Шаг 2: Настройка бэкенда в коде

Теперь вернемся к нашему проекту с EC2-инстансом из предыдущего урока и добавим в `main.tf` блок `backend`.

```hcl
# main.tf

terraform {
  # ... блок required_providers остается как был ...

  # Добавляем конфигурацию бэкенда
  backend "s3" {
    bucket         = "my-awesome-project-tfstate-2023" # УКАЖИТЕ ВАШЕ УНИКАЛЬНОЕ ИМЯ БАКЕТА
    key            = "global/ec2-project/terraform.tfstate" # Путь к файлу состояния внутри бакета
    region         = "us-east-1"
    dynamodb_table = "terraform-state-locks" # Имя таблицы для блокировок
    encrypt        = true
  }
}

# ... остальная часть файла (provider, data, resource) без изменений ...
```
*`key` — это путь внутри бакета. Хорошая практика — структурировать состояние по проектам или окружениям.*

## Команда-методичка

1.  **Переинициализация с миграцией**:
    После добавления блока `backend` нужно снова запустить `init`.
    ```bash
    terraform init
    ```
    *Ожидаемый результат*: Terraform обнаружит, что вы настроили бэкенд. Так как у вас уже есть локальный файл `terraform.tfstate`, Terraform спросит:
    `Do you want to copy existing state to the new backend?`
    Введите `yes`. Terraform скопирует ваше локальное состояние в S3 бакет и с этого момента будет работать только с ним. Локальный `terraform.tfstate` больше не нужен.

2.  **Проверка работы**:
    Запустите `plan` или `apply`.
    ```bash
    terraform plan
    ```
    *Ожидаемый результат*: Вы увидите сообщение `Acquiring state lock...`. Это означает, что механизм блокировки работает. План должен показать `No changes`, так как ваша инфраструктура уже соответствует коду.

3.  **Управление состоянием (полезные команды)**:
    Иногда нужно посмотреть, что находится в состоянии, или переместить ресурс.
    -   `terraform state list`: Показывает список всех ресурсов в состоянии.
    -   `terraform state show 'aws_instance.web_server'`: Показывает детали конкретного ресурса.

**Важно**: Теперь ваш файл `.tfstate` находится в S3. Папку `.terraform` и локальный `terraform.tfstate` (если остался) можно добавить в `.gitignore`, чтобы случайно не закоммитить их в репозиторий.

Теперь ваша команда может безопасно работать над одной инфраструктурой!
