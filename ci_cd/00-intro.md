# Тема 0: Введение в CI/CD

## Какую проблему решаем?

Представьте, что вы работаете в команде. Каждый пишет код, затем вручную:
1.  Проверяет, не сломал ли он что-то у коллег.
2.  Запускает тесты на своей машине.
3.  Собирает приложение.
4.  Заходит на сервер и копирует туда новые файлы.

Это долго, чревато ошибками ("а у меня на машине все работало!") и отвлекает от написания кода.

**CI/CD** — это практика, которая автоматизирует эти шаги, делая процесс разработки быстрым, надежным и предсказуемым.

## Основные концепции

*   **Continuous Integration (CI, Непрерывная Интеграция)**
    *   **Идея:** Разработчики регулярно (несколько раз в день) вливают свои изменения в общую ветку (`main` или `develop`).
    *   **Автоматизация:** Каждое такое вливание автоматически запускает сборку и тесты. Это позволяет быстро находить и исправлять ошибки интеграции.
    *   **Результат:** У вас всегда есть рабочая версия кода в основной ветке.

*   **Continuous Delivery/Deployment (CD, Непрерывная Доставка/Развертывание)**
    *   **Идея:** Продолжение CI. Если сборка и тесты прошли успешно, приложение автоматически готовится к релизу.
    *   **Continuous Delivery (Доставка):** Собранная версия приложения (артефакт) готова к развертыванию на `production` одним нажатием кнопки.
    *   **Continuous Deployment (Развертывание):** Собранная версия автоматически развертывается на `production` без участия человека.

## Компоненты CI/CD систем

| Термин | GitLab CI | GitHub Actions | Описание |
|---|---|---|---|
| **Pipeline** | Pipeline | Workflow | Весь процесс от начала до конца (например, "сборка -> тест -> деплой"). Состоит из этапов и задач. |
| **Stage** | Stage | (нет прямого аналога, но `jobs` могут зависеть друг от друга через `needs`) | Этап, который объединяет несколько задач. Задачи следующего этапа не начнутся, пока не завершатся все задачи предыдущего. |
| **Job** | Job | Job | Конкретная задача, выполняемая на раннере (например, "запустить тесты"). |
| **Runner/Agent** | Runner | Runner | Виртуальная машина или контейнер, где фактически выполняются ваши команды. GitLab и GitHub предоставляют свои раннеры, но можно подключить и собственные. |
| **Конфиг. файл** | `.gitlab-ci.yml` | `.github/workflows/*.yml` | Файл в корне репозитория, описывающий ваш pipeline/workflow. |

## GitLab CI vs. GitHub Actions

Обе системы очень мощные и похожи по своей сути, но есть ключевые различия в синтаксисе и подходе.

| Аспект | GitLab CI | GitHub Actions |
|---|---|---|
| **Структура** | Строгая иерархия: `stages` -> `jobs`. | Гибкая: `jobs` могут выполняться параллельно или зависеть друг от друга (`needs`). |
| **Конфигурация** | Один файл `.gitlab-ci.yml`. | Несколько файлов в `.github/workflows/`. Каждый файл — отдельный workflow. |
| **Переиспользование кода** | `include` для включения других YAML файлов, `extends` для наследования. | `uses` для использования готовых "экшенов" из Marketplace. Это ключевое преимущество GitHub. |
| **Среда выполнения** | `image`: `docker-образ`, в котором выполняется job. | `runs-on`: `ОС` (ubuntu-latest, windows-latest), на которой выполняется job. |
| **Команды** | `script`: массив команд для выполнения. | `run`: одна или несколько команд для выполнения. |
