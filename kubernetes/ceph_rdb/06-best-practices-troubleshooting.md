# 6. Лучшие практики, типичные ошибки и решение проблем

Правильная настройка и понимание подводных камней — ключ к стабильной и производительной работе хранилища Ceph RBD в Kubernetes.

## Лучшие практики (Best Practices)

### На уровне Ceph:
1.  **Изолируйте пулы**: Создавайте отдельные пулы для Kubernetes, и, если возможно, для разных типов данных (например, `k8s-ssd-pool`, `k8s-hdd-pool`). [20]
2.  **Правильно подбирайте количество PG**: Рассчитайте оптимальное количество Placement Groups (PG) для ваших пулов. Недостаточное или избыточное количество PG может негативно сказаться на производительности и стабильности кластера.
3.  **Используйте выделенного пользователя**: Никогда не используйте ключ `client.admin` в Kubernetes. Создайте пользователя с минимально необходимыми правами только для нужного пула. [9]
4.  **Размещайте мониторы на быстрых дисках**: Стабильность мониторов Ceph зависит от скорости их хранилища. Используйте SSD для `dataDirHostPath` мониторов. [28]

### На уровне Kubernetes и CSI:
5.  **Используйте несколько `StorageClass`**: Определите классы для разных уровней производительности (IOPS) или типов носителей (SSD/HDD), чтобы приложения могли запрашивать подходящее хранилище. [1]
6.  **Настройте CRUSH Map через лейблы узлов**: Для повышения отказоустойчивости разметьте узлы Kubernetes лейблами, соответствующими их физическому расположению (`topology.kubernetes.io/zone`, `rack`, `host`). Rook (популярный оператор для Ceph в K8s) может использовать эти лейблы для создания отказоустойчивой топологии CRUSH, чтобы реплики данных не оказались в одной стойке или зоне отказа. [28]
7.  **Используйте `host` network для производительности**: Для критичных к задержкам приложений можно настроить поды Ceph (особенно OSD) на использование сети хоста (`hostNetwork: true`). Это снижает сетевые накладные расходы. [28]
8.  **Управляйте ресурсами подов Ceph**: Задавайте запросы (requests) и лимиты (limits) по CPU и памяти для компонентов Ceph (OSD, MON), чтобы Kubernetes мог корректно планировать нагрузки и избегать "шумных соседей". [28]

## Распространенные ошибки (Bad Practices)

1.  **Использование `client.admin`**: Самая частая и опасная ошибка. Компрометация секрета в Kubernetes приведет к компрометации всего Ceph-кластера.
2.  **Использование пула `rbd` по умолчанию**: Этот пул может использоваться другими сервисами. Смешивание данных Kubernetes с другими данными затрудняет управление.
3.  **Неинициализированный пул**: Если пул не инициализирован командой `rbd pool init`, CSI-драйвер не сможет с ним работать. [1]
4.  **`reclaimPolicy: Retain` без контроля**: Если использовать `Retain` и бесконтрольно удалять PVC, ваш Ceph-кластер быстро заполнится "осиротевшими" RBD-образами, которые придется чистить вручную.
5.  **Несоответствие `clusterID`**: Если `clusterID` (FSID) в `StorageClass` или `ConfigMap` не совпадает с реальным FSID кластера Ceph, драйвер не сможет к нему подключиться.

## Решение проблем (Troubleshooting)

### Проблема: PVC застрял в статусе `Pending`

**Возможные причины:**
*   Не запущены поды `csi-rbdplugin-provisioner`.
*   Проблемы с доступом к Ceph-кластеру.
*   Неправильный `Secret` или `ConfigMap`.

**Диагностика:**
1.  **Проверьте поды прови저нера:**
    ```bash
    kubectl get pods -l app=csi-rbdplugin-provisioner -n <namespace>
    ```
    Убедитесь, что они в статусе `Running`.
2.  **Посмотрите логи прови저нера:**
    ```bash
    kubectl logs -l app=csi-rbdplugin-provisioner -c csi-provisioner -n <namespace>
    ```
    Ищите сообщения об ошибках аутентификации, недоступности мониторов или неправильном имени пула.
3.  **Проверьте `StorageClass` и `Secret`:**
    Убедитесь, что имя пула, `clusterID`, и данные в `Secret` указаны верно.

### Проблема: Под не может запуститься, ошибка `MountVolume.SetUp failed`

**Возможные причины:**
*   Проблема на узле Kubernetes, где запланирован под.
*   Сетевая недоступность Ceph-мониторов с рабочего узла.
*   Отсутствует ядерный модуль `rbd`.

**Диагностика:**
1.  **Проверьте поды CSI на узле:**
    Найдите узел, на котором "застрял" ваш под (`kubectl get pod <pod-name> -o wide`). Затем проверьте под `csi-rbdplugin` на этом узле:
    ```bash
    kubectl get pods -l app=csi-rbdplugin --field-selector spec.nodeName=<node-name> -n <namespace>
    ```
2.  **Посмотрите логи `csi-rbdplugin` на этом узле:**
    ```bash
    kubectl logs <csi-rbdplugin-pod-name> -c csi-rbdplugin -n <namespace>
    ```
    В логах будут видны команды `rbd map`, которые он пытается выполнить, и ошибки, если они есть.
3.  **Проверьте связность с узла:**
    Зайдите на проблемный узел (через `ssh`) и попробуйте подключиться к мониторам Ceph:
    ```bash
    # Установите ceph-common, если необходимо
    sudo apt install ceph-common
    # Проверьте статус кластера с узла
    ceph -m <monitor_ip:port> -s
    ```
4.  **Проверьте наличие модуля `rbd`:**
    На рабочем узле выполните:
    ```bash
    lsmod | grep rbd
    ```
    Если вывод пуст, значит модуль ядра не загружен, что может указывать на проблемы с ядром или его конфигурацией. CSI-драйвер по умолчанию использует этот модуль. [1]
