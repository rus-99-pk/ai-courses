# 1. Введение в Ceph RBD и его роль в Kubernetes

Этот раздел закладывает основу для понимания того, что такое Ceph RBD и почему это мощное решение для персистентного хранения данных в Kubernetes.

## Что такое Ceph и Ceph RBD?

**Ceph** — это унифицированная, распределенная программно-определяемая система хранения данных (SDS) с открытым исходным кодом. [4] Она спроектирована для обеспечения высокой производительности, надежности и масштабируемости. [4, 11] Ceph может предоставлять хранилище данных в трех форматах: [4]

1.  **Объектное хранилище (RADOS Gateway)**: S3/Swift-совместимый интерфейс.
2.  **Блочное хранилище (RBD)**: RADOS Block Devices — то, на чем мы фокусируемся в этом курсе.
3.  **Файловое хранилище (CephFS)**: POSIX-совместимая распределенная файловая система.

**Ceph RBD (RADOS Block Device)** предоставляет блочные устройства, которые можно подключать к серверам или виртуальным машинам. [2] Ключевая особенность RBD в том, что данные образа блочного устройства "нарезаются" на части (объекты) и распределяются по всему кластеру Ceph. [1] Это обеспечивает высокую производительность и отказоустойчивость, так как нет единой точки отказа. [1]

Ключевые возможности Ceph RBD включают тонкое выделение пространства (thin provisioning), изменение размера "на лету" и создание снэпшотов (моментальных снимков). [2, 4]

## Зачем использовать Ceph RBD с Kubernetes?

Kubernetes — это система для автоматизации развертывания, масштабирования и управления контейнеризированными приложениями. [2] Когда речь заходит о приложениях с состоянием (stateful applications), таких как базы данных, возникает острая необходимость в надежном и постоянном хранилище данных. [2]

Ceph RBD идеально подходит на роль такого хранилища по нескольким причинам:

*   **Динамическое выделение томов (Dynamic Provisioning)**: Kubernetes может автоматически создавать и подключать тома Ceph RBD по запросу от приложений, без ручного вмешательства администратора. [11]
*   **Высокая доступность и отказоустойчивость**: Данные в Ceph реплицируются или используют коды избыточности (erasure coding), что обеспечивает их сохранность даже при выходе из строя отдельных дисков или целых серверов. [11]
*   **Масштабируемость**: Ceph-кластер можно легко расширять, добавляя новые диски или узлы, что позволяет наращивать емкость и производительность хранилища по мере роста потребностей. [11]
*   **Производительность**: Благодаря распределению данных по множеству дисков (OSD), операции чтения и записи могут выполняться параллельно, обеспечивая высокую скорость доступа. [11]
*   **Продвинутые функции**: Поддержка снэпшотов, клонирования и расширения томов "на лету" предоставляет гибкие возможности для резервного копирования, восстановления и управления данными. [2, 9]

## Архитектура интеграции: Как это работает?

Связь между Kubernetes и Ceph осуществляется через **Container Storage Interface (CSI)**. [6] CSI — это стандартный API, который позволяет системам оркестрации контейнеров, таким как Kubernetes, взаимодействовать с различными системами хранения. [6, 8]

Для интеграции с Ceph используется `ceph-csi` драйвер. [1] Устаревший встроенный прови저нер (`kubernetes.io/rbd`) больше не рекомендуется к использованию. [6]

Компоненты `ceph-csi` в Kubernetes:

1.  **CSI Controller Plugin**: Это Deployment из нескольких подов, который отвечает за управление томами: создание, удаление, подключение/отключение, создание снэпшотов. Он напрямую взаимодействует с API Ceph-кластера.
2.  **CSI Node Plugin**: Это DaemonSet, который запускает по одному поду на каждом рабочем узле Kubernetes. Он отвечает за монтирование RBD-устройства к конкретному узлу, чтобы под, запущенный на этом узле, мог его использовать.

Процесс работы выглядит следующим образом:

1.  Разработчик создает `PersistentVolumeClaim` (PVC), запрашивая том определенного размера и класса.
2.  Kubernetes передает этот запрос CSI-драйверу.
3.  CSI Controller Plugin создает образ RBD в указанном пуле Ceph.
4.  Затем он создает `PersistentVolume` (PV) — объект Kubernetes, представляющий этот RBD-образ.
5.  Kubernetes связывает PV и PVC.
6.  Когда под, использующий этот PVC, планируется на узел, Kubernetes дает команду CSI-драйверу "подключить" том.
7.  CSI Controller Plugin разрешает подключение тома к узлу.
8.  CSI Node Plugin на этом узле выполняет команду для отображения (map) RBD-устройства и его монтирования в нужную директорию внутри пода.
