## Модуль 2: Установка Istio и Observability Stack

На этом этапе мы превратим обычный Kubernetes кластер в Service Mesh. Мы не просто установим Istio, но и развернем полный стек наблюдения (Observability). Без него Istio — это просто "черный ящик", который усложняет систему. Стек наблюдения делает её прозрачной.

### 2.1 Профиль установки Istio
Мы будем использовать профиль `demo`.

```bash
# Установка Istio с профилем demo
istioctl install --set profile=demo -y
```

**Что именно мы установили?**
1.  **Istiod (Control Plane):** "Мозг" системы. Он раздает конфигурации прокси-серверам, управляет сертификатами (CA) для шифрования и правилами маршрутизации.
2.  **Ingress Gateway:** Входная дверь в кластер (LoadBalancer), через которую внешний трафик попадает внутрь Mesh.
3.  **Egress Gateway:** Выходная дверь. Весь трафик из кластера во внешний мир проходит через неё (полезно для аудита внешних запросов).

> **Почему `demo`?** В этом профиле включены максимальные настройки логирования и трассировки. В профиле `default` (для продакшена) они часто отключены или семплируются (записывается 1 запрос из 100) для экономии ресурсов. Для обучения нам нужно видеть 100% происходящего.

### 2.2 Разбор компонентов Observability (Теория)
Istio генерирует огромное количество телеметрии. Чтобы с ней работать, нам нужны 4 ключевых инструмента, которые ставятся как аддоны.

1.  **Prometheus (База данных метрик):**
    *   *Роль:* Сборщик и хранитель.
    *   *Как работает:* Каждые несколько секунд опрашивает все Envoy-прокси и сохраняет их показатели (количество запросов, коды ответов 200/500, потребление CPU). Сам по себе не имеет красивого интерфейса.

2.  **Grafana (Визуализация метрик):**
    *   *Роль:* Красивые графики.
    *   *Как работает:* Подключается к Prometheus, берет сырые цифры и строит дашборды: "Сколько ошибок в секунду", "Среднее время ответа".

3.  **Kiali (Консоль управления и Топология):**
    *   *Роль:* Главный UI для Istio.
    *   *Как работает:* Это "клей", который собирает всё воедино.
        *   Рисует карту сервисов (кто с кем общается), используя метрики **Prometheus**.
        *   Показывает трассы запросов, подтягивая их из **Jaeger** (если развернут).
        *   Позволяет валидировать конфигурации Istio (YAML файлы).

### 2.3 Установка аддонов (Практика)
Применим манифесты из официального репозитория Istio.

```bash
# Устанавливаем компоненты по очереди
kubectl apply -f https://raw.githubusercontent.com/istio/istio/master/samples/addons/prometheus.yaml
kubectl apply -f https://raw.githubusercontent.com/istio/istio/master/samples/addons/grafana.yaml
kubectl apply -f https://raw.githubusercontent.com/istio/istio/master/samples/addons/kiali.yaml
```

*Примечание: Если вы видите сообщения `created` — всё идет по плану. Если `unchanged` — значит, вы применили команду повторно.*

### 2.4 Проверка установки
Убедимся, что все компоненты запустились и готовы к работе. Все они живут в неймспейсе `istio-system`.

```bash
kubectl get pods -n istio-system
```

**Ожидаемый результат:**
Вы должны увидеть список подов со статусом `Running`. Важно дождаться, пока `READY` будет `1/1` (или `2/2` для некоторых).

Пример вывода:
```text
NAME                                   READY   STATUS    RESTARTS   AGE
grafana-xxxxxxxxx-xxxxx                1/1     Running   0          2m
istio-egressgateway-xxxx-xxxx          1/1     Running   0          5m
istio-ingressgateway-xxxx-xxxx         1/1     Running   0          5m
istiod-xxxxxxxxx-xxxxx                 1/1     Running   0          5m
kiali-xxxxxxxxx-xxxxx                  1/1     Running   0          2m
prometheus-xxxxxxxxx-xxxxx             2/2     Running   0          2m
```

Если какой-то под находится в статусе `Pending` или `ContainerCreating` слишком долго (больше 2-3 минут) — проверьте, хватает ли Docker-у ресурсов (CPU/Memory).
