# Файл 5: Архитектура безопасности Kubernetes и модель 4C

Переход от Docker к Kubernetes (K8s) означает переход от управления отдельными контейнерами к оркестрации целых систем. Это вносит новые уровни сложности и, соответственно, новые аспекты безопасности. [9]

## 1. Модель 4C's of Cloud Native Security

Чтобы структурировать подход к безопасности в Kubernetes, принято использовать модель "4C", где каждый слой строится на безопасности предыдущего. [2, 3] Уязвимость на внешнем слое (Cloud) делает все внутренние слои (Cluster, Container, Code) небезопасными.

![4Cs of Security](https://i.imgur.com/E8aVl4L.png)

1.  **Cloud (Облако / Инфраструктура):**
    *   **Описание:** Это самый нижний, фундаментальный слой. Он включает физическую безопасность дата-центров, безопасность сети провайдера и безопасность гипервизоров.
    *   **Задачи:** Защита физической инфраструктуры, сетевая сегментация на уровне провайдера (VPC, Security Groups), безопасная конфигурация IaaS.
    *   **Ответственность:** В основном лежит на облачном провайдере (AWS, GCP, Azure), но **вы** несете ответственность за правильную конфигурацию предоставляемых им сервисов.

2.  **Cluster (Кластер):**
    *   **Описание:** Этот слой охватывает безопасность компонентов самого Kubernetes, как Control Plane, так и Worker Nodes. [7]
    *   **Задачи:** Защита API Server, etcd, kubelet; настройка RBAC; использование Network Policies; управление секретами.
    *   **Ответственность:** Совместная. Облачный провайдер отвечает за безопасность managed Control Plane (в EKS, GKE, AKS), а **вы** — за конфигурацию безопасности кластера и защиту Worker Nodes.

3.  **Container (Контейнер):**
    *   **Описание:** Безопасность непосредственно во время сборки и выполнения контейнера.
    *   **Задачи:** Сканирование образов, использование минимальных образов, runtime security, ограничение привилегий.
    *   **Ответственность:** Полностью **ваша**. Это все, что мы обсуждали в предыдущих модулях.

4.  **Code (Код):**
    *   **Описание:** Безопасность самого приложения, работающего внутри контейнера. [10]
    *   **Задачи:** Защита от SQL-инъекций, XSS; управление зависимостями (SCA); статический анализ кода (SAST); шифрование трафика (TLS). [11]
    *   **Ответственность:** В основном лежит на разработчиках, но DevOps-инженеры предоставляют инструменты и пайплайны для автоматической проверки безопасности кода.

## 2. Модель разделения ответственности (Shared Responsibility Model)

При использовании управляемых Kubernetes-сервисов (EKS, GKE, AKS) крайне важно понимать, за что отвечает облачный провайдер, а за что — вы. [14, 22, 23, 24]

| Компонент | Ответственность Провайдера (EKS, GKE, AKS) | Ваша Ответственность |
| :--- | :--- | :--- |
| **Control Plane (API Server, etcd, Scheduler)** | Установка, управление, масштабирование, обновление, безопасность компонентов. | — |
| **Worker Nodes (OS)** | Предоставление защищенных образов ОС (например, Bottlerocket, COS). | Обновление ОС на нодах, применение патчей безопасности, настройка `kubelet`. |
| **Сетевая конфигурация** | Безопасность базовой сети (VPC). | Настройка Security Groups, Network Policies, Ingress controllers. |
| **IAM и RBAC** | Предоставление сервиса IAM. | Создание и управление IAM ролями, настройка RBAC правил внутри кластера. |
| **Данные и Приложения** | — | Безопасность кода, контейнеров, управление секретами, шифрование данных приложения. |
| **Мониторинг и Логирование** | Предоставление сервисов (CloudWatch, Cloud Logging). | Настройка сбора логов и метрик, создание алертов. |

**Нюанс для Middle DevOps:** Ваша зона ответственности начинается с конфигурации Worker Nodes и всего, что находится "внутри" кластера. Вы не управляете `etcd` напрямую в managed-сервисах, но вы несете полную ответственность за то, кто и как может получить к нему доступ через API Server.

## 3. Архитектура безопасности Kubernetes: ключевые компоненты

Чтобы защищать кластер, нужно понимать его архитектуру и потенциальные точки отказа. [4, 9]

![Kubernetes Architecture](https://i.imgur.com/gK9oD4k.png)

### 3.1. Control Plane

Это "мозг" кластера. Его компрометация означает полную потерю контроля. [20]

*   **API Server (`kube-apiserver`):**
    *   **Роль:** Единственная точка входа для всех операций в кластере. Валидирует и обрабатывает все REST-запросы.
    *   **Векторы атак:** Неавторизованный доступ, DoS-атаки, обход аутентификации/авторизации.
    *   **Защита:** Включение аутентификации и авторизации (RBAC), использование TLS для всего трафика, ограничение сетевого доступа (firewall), включение аудита. [9, 21]

*   **etcd:**
    *   **Роль:** Распределенное key-value хранилище, где хранится все состояние кластера: все объекты (Pods, Secrets, ConfigMaps и т.д.). [18]
    *   **Векторы атак:** Прямой неавторизованный доступ к базе данных, чтение секретов в открытом виде.
    *   **Защита:** Доступ к `etcd` должен быть **только** у API Server. [6, 20] Весь трафик между API Server и etcd должен быть зашифрован с помощью mTLS. [5, 13, 18] Необходимо включать шифрование секретов в `etcd` на уровне хранения (Encryption at Rest). [6, 15, 17]

*   **Controller Manager & Scheduler:**
    *   **Роль:** Управляют жизненным циклом объектов и размещением подов.
    *   **Защита:** Работают внутри Control Plane и общаются только с API Server. Их основная защита — это защита самого API Server.

### 3.2. Worker Nodes

Это машины, на которых запускаются ваши контейнеры.

*   **Kubelet:**
    *   **Роль:** Агент, работающий на каждой ноде. Управляет подами и контейнерами на своей ноде по командам от API Server.
    *   **Векторы атак:** Анонимный доступ, который может позволить злоумышленнику запускать команды на ноде.
    *   **Защита:** Запретить анонимный доступ (`--anonymous-auth=false`), использовать строгие права для `kubelet` (Node authorizer).

*   **Container Runtime (containerd, CRI-O):**
    *   **Роль:** Движок, который непосредственно запускает и останавливает контейнеры (например, `containerd`).
    *   **Защита:** Все, что мы обсуждали в модуле по Runtime Security (Seccomp, AppArmor, и т.д.).

### Команды-методички

**Проверить, включено ли шифрование секретов в etcd (Encryption at Rest):**
Это делается через конфигурацию API Server. Если вы используете managed-сервис, обычно это включено по умолчанию. Для self-hosted кластера нужно проверить флаг `--encryption-provider-config` в манифесте `kube-apiserver`.

**Проверить, разрешен ли анонимный доступ к Kubelet:**
Подключитесь к worker ноде и выполните:
```bash
# Попытка получить доступ к kubelet API без аутентификации
curl -k https://localhost:10250/pods

# Если вы получили ответ "Unauthorized", значит анонимный доступ отключен (это хорошо).
# Если вы получили список подов, это серьезная уязвимость.
```
