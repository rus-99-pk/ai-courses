# Файл 8: Управление Секретами в Kubernetes

Неправильное управление секретами (пароли, API-ключи, TLS-сертификаты) — один из самых распространенных и опасных рисков в любой системе, и Kubernetes не исключение.

**Ключевые задачи, которые мы решаем:**

*   **Предотвращение "захардкоженных" секретов:** Исключение хранения чувствительных данных напрямую в Docker-образах, YAML-манифестах или в системе контроля версий.
*   **Безопасное хранение:** Обеспечение того, чтобы секреты хранились в зашифрованном виде.
*   **Контроль доступа:** Предоставление доступа к секретам только тем подам и пользователям, которым он действительно необходим.
*   **Аудит и ротация:** Возможность отслеживать, кто и когда получал доступ к секрету, и легко обновлять (ротировать) секреты без простоя приложений.

---

## 1. Встроенный механизм: Kubernetes Secrets

Kubernetes предоставляет встроенный объект `Secret` для хранения и управления чувствительной информацией. [2, 5]

**Важный нюанс:** По умолчанию `Secret` в Kubernetes — это просто объект в etcd, закодированный в **Base64**. Base64 — это **не шифрование**, а всего лишь кодировка. Любой, кто имеет доступ к `etcd` или может прочитать объект `Secret` через API, может легко его декодировать.

```bash
# Пример "небезопасности" Base64
echo 'my-super-secret-password' | base64
# Вывод: bXktc3VwZXItc2VjcmV0LXBhc3N3b3JkCg==

echo 'bXktc3VwZXItc2VjcmV0LXBhc3N3b3JkCg==' | base64 --decode
# Вывод: my-super-secret-password
```

### Как сделать Kubernetes Secrets безопаснее?

1.  **Включите шифрование в etcd (Encryption at Rest):** Это самая важная мера. Администратор кластера должен настроить API Server так, чтобы он шифровал объекты `Secret` перед записью в `etcd`. [4, 9, 19]
2.  **Используйте RBAC:** Строго ограничьте, кто (пользователи и ServiceAccounts) имеет права `get`, `list` и `watch` для объектов `Secret`. [1, 4]

### Способы использования Secrets в Подах

Существует три основных способа передать секрет в под: [2, 3]

1.  **Как переменные окружения (Environment Variables):**
    *   **Плюсы:** Просто и удобно для многих приложений.
    *   **Минусы:** Секреты могут "утечь" через логи, вывод команды `env` внутри контейнера или через дочерние процессы. [17]

2.  **Как файлы в смонтированном томе (Volume Mounts):**
    *   **Плюсы:** Считается более безопасным методом. Секреты монтируются как файлы в память (`tmpfs`), и вы можете контролировать права доступа к ним.
    *   **Минусы:** Приложению нужно уметь читать конфигурацию из файлов.

3.  **Как `imagePullSecrets`:**
    *   **Использование:** Для предоставления поду кредов для скачивания образов из приватных Docker-репозиториев. [2]

### Практический пример и команды-методички

**1. Создание секрета:**

```bash
# Из литералов (удобно для простых пар ключ-значение)
kubectl create secret generic db-credentials \
  --from-literal=username=postgres \
  --from-literal=password='S3cr3tP@ssw0rd!'

# Из файлов (удобно для сертификатов, конфигурационных файлов)
echo -n 'postgres' > ./username.txt
echo -n 'S3cr3tP@ssw0rd!' > ./password.txt
kubectl create secret generic db-credentials-from-file --from-file=./username.txt --from-file=./password.txt
```

**2. Использование секрета в Поде (оба способа):**

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: my-app-pod
spec:
  containers:
  - name: my-app-container
    image: my-app
    env:
      - name: DB_USERNAME # Переменная окружения
        valueFrom:
          secretKeyRef:
            name: db-credentials # Имя секрета
            key: username       # Ключ внутри секрета
      - name: DB_PASSWORD
        valueFrom:
          secretKeyRef:
            name: db-credentials
            key: password
    volumeMounts:
    - name: secret-volume
      mountPath: "/etc/secrets" # Монтируем как файлы в директорию
      readOnly: true
  volumes:
  - name: secret-volume
    secret:
      secretName: db-credentials
```

**3. Проверка внутри пода:**

```bash
# Заходим в под
kubectl exec -it my-app-pod -- /bin/sh

# Проверяем переменные окружения
/ # echo $DB_USERNAME
postgres

# Проверяем смонтированные файлы
/ # ls /etc/secrets
password
username
/ # cat /etc/secrets/password
S3cr3tP@ssw0rd!
```

## 2. Продвинутое управление секретами: Внешние хранилища

Хотя встроенные `Secrets` можно сделать достаточно безопасными, у них есть ограничения, особенно в больших или сложных средах. [18]

**Проблемы, которые мы решаем:**

*   **Централизованное хранение:** Управление секретами для нескольких кластеров и сред (dev, stage, prod) из одного места.
*   **Динамические секреты:** Автоматическая генерация временных кредов для доступа к базам данных или облачным сервисам.
*   **Строгий аудит и ротация:** Продвинутые возможности для отслеживания доступа и автоматического обновления секретов. [1, 9]

### Популярные решения

1.  **HashiCorp Vault:**
    *   **Описание:** "Золотой стандарт" в мире управления секретами. Предоставляет шифрование, динамические секреты, строгие политики доступа и многое другое. [6, 8]
    *   **Интеграция с K8s:** Поды аутентифицируются в Vault через свои Service Accounts. Vault Agent (в режиме `init` или `sidecar` контейнера) получает секреты и передает их приложению. [7, 11]

2.  **Облачные провайдеры (AWS Secrets Manager, Azure Key Vault, GCP Secret Manager):**
    *   **Описание:** Нативные сервисы от облачных провайдеров.
    *   **Интеграция с K8s:** Обычно осуществляется через специализированные драйверы или операторы.

### Шаблон интеграции: External Secrets Operator (ESO)

**External Secrets Operator** — это популярный open-source проект, который "синхронизирует" секреты из внешних хранилищ (Vault, AWS SM, Azure KV и др.) в нативные Kubernetes `Secrets`. [12, 14]

**Как это работает:**
1.  Вы устанавливаете ESO в свой кластер. [15]
2.  Вы создаете `SecretStore` (или `ClusterSecretStore`), который описывает, как подключаться к вашему внешнему хранилищу (например, URL Vault и метод аутентификации).
3.  Вы создаете `ExternalSecret`, который говорит: "возьми секрет `path/to/my/db-password` из Vault и создай Kubernetes `Secret` с именем `db-credentials`".
4.  ESO автоматически создает и обновляет нативный `Secret`.
5.  Ваше приложение использует этот нативный `Secret` как обычно (через env или volume mount), ничего не зная о Vault.

**Преимущества этого подхода:**
*   **Разделение ответственности:** DevOps управляют `SecretStore` и `ExternalSecret`, а приложения остаются "Kubernetes-нативными".
*   **Централизация:** Секреты по-прежнему управляются централизованно во внешнем хранилище.
*   **Автоматизация:** Секреты автоматически обновляются в кластере при их изменении во внешнем источнике. [16]

**Пример манифеста `ExternalSecret`:**

```yaml
apiVersion: external-secrets.io/v1beta1
kind: ExternalSecret
metadata:
  name: my-app-db-credentials
spec:
  refreshInterval: "1h" # Как часто проверять обновления
  secretStoreRef:
    name: vault-backend # Ссылка на SecretStore
    kind: SecretStore
  target:
    name: db-credentials # Имя создаваемого Kubernetes Secret
  data:
  - secretKey: username
    remoteRef:
      key: secret/data/myapp/db # Путь к секрету в Vault
      property: username       # Поле внутри секрета
  - secretKey: password
    remoteRef:
      key: secret/data/myapp/db
      property: password
```
