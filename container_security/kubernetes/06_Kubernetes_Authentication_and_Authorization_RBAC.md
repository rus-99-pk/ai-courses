# Файл 6: Аутентификация и Авторизация в Kubernetes (RBAC)

Доступ к Kubernetes API — это ключ ко всему кластеру. Контроль над тем, **кто** может выполнять **какие** действия, является основой безопасности K8s. Этот процесс делится на два этапа:

1.  **Аутентификация (Authentication, AuthN):** Ответ на вопрос "Кто ты?". Проверка личности пользователя, сервиса или машины, отправляющей запрос к API. [23]
2.  **Авторизация (Authorization, AuthZ):** Ответ на вопрос "Что тебе можно делать?". Проверка, имеет ли аутентифицированный субъект права на выполнение запрошенной операции. [7]

## 1. Аутентификация (Кто ты?)

Kubernetes не имеет встроенной системы управления пользователями. Он делегирует аутентификацию внешним системам или использует предоставленные механизмы. [19, 21]

### Типы субъектов в Kubernetes

*   **User Accounts (Пользователи):** Предназначены для людей (администраторы, разработчики). Они глобальны для кластера и не управляются как объекты K8s. [11, 15] Их identities обычно приходят из внешних систем.
*   **Service Accounts (Сервисные Аккаунты):** Предназначены для процессов, работающих внутри подов (например, для CI/CD пайплайна или для приложения, которому нужно обращаться к K8s API). Они являются объектами K8s, привязанными к конкретному Namespace. [12, 14, 15]

### Способы аутентификации

| Метод | Описание | Плюсы | Минусы |
| :--- | :--- | :--- | :--- |
| **X.509 Сертификаты** | Клиент предоставляет TLS-сертификат, подписанный доверенным CA кластера. `kubeconfig` файлы часто используют этот метод. [5, 10] | Очень безопасно. | Сложное управление: отзыв сертификатов, перевыпуск по истечении срока. [5] |
| **Bearer Токены** | Клиент передает токен в заголовке `Authorization`. API Server проверяет его валидность. | Просто в использовании. | Токены могут быть украдены. |
| **Service Account Токены** | Частный случай Bearer токенов, автоматически создаются для ServiceAccounts и монтируются в поды. | Автоматизировано, идеально для внутрикластерного взаимодействия. [5] | По умолчанию токены могут быть слишком "долгоживущими". |
| **OpenID Connect (OIDC)** | Интеграция с внешними Identity-провайдерами (Okta, Auth0, Google, Azure AD). [21, 23] | Централизованное управление пользователями, поддержка SSO, MFA. | Требует настройки внешнего провайдера и API Server. |

**Лучшая практика:** Для пользователей-людей использовать **OIDC** для интеграции с корпоративной системой управления учетными записями. Для сервисов внутри кластера — **Service Accounts**.

## 2. Авторизация (Что можно делать?): Role-Based Access Control (RBAC)

После того как API Server аутентифицировал субъект, ему нужно решить, разрешить ли запрашиваемое действие. Стандартом для этого в Kubernetes является **RBAC**. [2, 16]

### Ключевые объекты RBAC

RBAC оперирует четырьмя основными видами объектов:

1.  **Role (Роль):**
    *   **Что это:** Набор правил, описывающих, какие действия (`verbs`: `get`, `list`, `create`, `delete`) можно выполнять над какими ресурсами (`resources`: `pods`, `services`, `secrets`).
    *   **Область действия:** **Namespace**. `Role` действует только в том неймспейсе, в котором она создана.

2.  **ClusterRole (Кластерная Роль):**
    *   **Что это:** То же, что и `Role`, но с одним отличием.
    *   **Область действия:** **Весь кластер**. Используется для предоставления доступа к:
        *   Ресурсам в нескольких неймспейсах (например, `pods` во всех неймспейсах).
        *   Ресурсам, не привязанным к неймспейсу (`nodes`, `persistentvolumes`).
        *   Не-ресурсным URL (`/healthz`, `/metrics`).

3.  **RoleBinding (Привязка Роли):**
    *   **Что это:** "Склеивает" `Role` с субъектом (User, Group, ServiceAccount).
    *   **Действие:** Предоставляет права из `Role` указанному субъекту **внутри неймспейса**, где создан `RoleBinding`.

4.  **ClusterRoleBinding (Привязка Кластерной Роли):**
    *   **Что это:** "Склеивает" `ClusterRole` с субъектом.
    *   **Действие:** Предоставляет права из `ClusterRole` указанному субъекту **во всем кластере**.

## 3. RBAC: Лучшие и плохие практики

### Лучшие практики

*   **Принцип наименьших привилегий (Least Privilege):** Всегда предоставляйте только те права, которые абсолютно необходимы. [1, 13, 15] Начинайте с пустой роли и добавляйте права по одному.
*   **Предпочитайте `Role` и `RoleBinding`:** По возможности всегда используйте роли, ограниченные неймспейсом. `ClusterRoleBinding` — очень мощный инструмент, используйте его с осторожностью. [1]
*   **Не используйте `default` ServiceAccount:** По умолчанию в каждом неймспейсе есть `default` ServiceAccount. Не давайте ему права. Для каждого приложения, которому нужен доступ к API, создавайте отдельный, выделенный `ServiceAccount`. [14]
*   **Используйте группы:** Управляйте правами пользователей через группы (например, из OIDC), а не по именам отдельных пользователей. [4]
*   **Избегайте wildcard (`*`):** Не используйте `"*"` в `resources` или `verbs`. Это дает слишком много прав, включая доступ к ресурсам, которые могут появиться в будущем. [4]
*   **Регулярный аудит:** Периодически проверяйте и пересматривайте выданные права. [6, 13]

### Плохая практика: Дать права "на всякий случай"

**Пример:** Разработчику нужно смотреть логи подов в неймспейсе `dev`.

**ПЛОХО:** Дать ему права `cluster-admin` или полные права на все ресурсы в неймспейсе.

```yaml
# ПЛОХО: СЛИШКОМ МНОГО ПРАВ
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: dev
  name: dev-overkill-role
rules:
- apiGroups: ["*"]
  resources: ["*"]
  verbs: ["*"]
```

**ХОРОШО:** Создать `Role`, которая разрешает только чтение подов и их логов.

```yaml
# ХОРОШО: Принцип наименьших привилегий
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: dev
  name: pod-reader-role
rules:
- apiGroups: [""] # "" означает core API group
  resources: ["pods", "pods/log"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-pods-binding
  namespace: dev
subjects:
- kind: User
  name: "developer@example.com" # Имя пользователя
  apiGroup: rbac.authorization.k8s.io
roleRef:
  kind: Role
  name: pod-reader-role
  apiGroup: rbac.authorization.k8s.io
```

## 4. Команды-методички (kubectl)

**Проверить, какое действие можно выполнить:**
Команда `kubectl auth can-i` — ваш лучший друг для отладки RBAC. [3, 17, 22, 24]

```bash
# Могу ли я (текущий пользователь) создавать Deployments в текущем неймспейсе?
kubectl auth can-i create deployments

# Могу ли я удалять Secrets во всех неймспейсах? (требует прав на list namespaces)
kubectl auth can-i delete secrets --all-namespaces

# Что может делать ServiceAccount 'prometheus-k8s' в неймспейсе 'monitoring'?
kubectl auth can-i list pods --namespace monitoring --as=system:serviceaccount:monitoring:prometheus-k8s
```

**Показать все свои права в неймспейсе:**

```bash
# Очень полезная команда для понимания, что вам разрешено
kubectl auth can-i --list --namespace=my-app
```

**Просмотреть существующие роли и привязки:**

```bash
# Посмотреть все роли в неймспейсе 'dev'
kubectl get roles -n dev

# Посмотреть все привязки в неймспейсе 'dev'
kubectl get rolebindings -n dev

# Описать роль, чтобы увидеть ее правила
kubectl describe role pod-reader-role -n dev
```
