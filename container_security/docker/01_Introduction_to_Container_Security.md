# Файл 1: Введение в безопасность контейнеров

## 1. Зачем нужна безопасность контейнеров?

Контейнеры изменили подход к разработке, развертыванию и масштабированию приложений, обеспечив беспрецедентную скорость и гибкость. [12] Однако, как и любая технология, они несут в себе новые риски и векторы атак. Безопасность контейнеров — это не опция, а критическая необходимость для защиты приложений, данных и инфраструктуры. [1, 4]

**Ключевые задачи, которые мы решаем:**

*   **Защита от уязвимостей:** Предотвращение эксплуатации уязвимостей в базовых образах, зависимостях приложений и самой среде выполнения контейнеров.
*   **Изоляция и сдерживание:** Обеспечение того, чтобы скомпрометированный контейнер не смог повлиять на хост-систему или другие контейнеры. [1, 14]
*   **Соответствие стандартам (Compliance):** Выполнение требований регуляторов (например, PCI DSS, GDPR, HIPAA), которые распространяются и на контейнеризированные среды. [4]
*   **Предотвращение утечек данных:** Защита секретов, конфигураций и конфиденциальных данных от несанкционированного доступа. [5]
*   **Обеспечение целостности:** Гарантия того, что в production запускаются только доверенные и проверенные образы. [3]

### Нюансы для Middle DevOps

На уровне Middle вы должны понимать, что безопасность — это не разовое действие, а непрерывный процесс, интегрированный во все этапы жизненного цикла приложения (DevSecOps). [6, 9] Ваша задача — не просто реагировать на инциденты, а выстраивать превентивные меры защиты.

## 2. Жизненный цикл контейнера и точки контроля безопасности

Безопасность должна встраиваться на каждом этапе жизненного цикла контейнеризированного приложения.

![Container Lifecycle Security](https://i.imgur.com/7g2J9bB.png)

1.  **Сборка (Build):**
    *   **Задачи:** Создание безопасного "золотого" образа.
    *   **Угрозы:** Использование уязвимых базовых образов, небезопасные инструкции в Dockerfile, встраивание секретов в образ. [12]
    *   **Контроль:** Анализ Dockerfile, сканирование образов на уязвимости.

2.  **Публикация (Ship/Push):**
    *   **Задачи:** Безопасное хранение и распространение образов.
    *   **Угрозы:** Загрузка вредоносных образов в репозиторий, отсутствие контроля версий, использование публичных непроверенных образов. [2, 8]
    *   **Контроль:** Использование приватных репозиториев, подпись образов, сканирование репозитория.

3.  **Развертывание (Deploy):**
    *   **Задачи:** Безопасная конфигурация и запуск контейнеров в оркестраторе.
    *   **Угрозы:** Неправильная конфигурация сети, избыточные привилегии, отсутствие политик безопасности.
    *   **Контроль:** Использование политик безопасности (Pod Security Standards, Network Policies), настройка RBAC.

4.  **Выполнение (Run):**
    *   **Задачи:** Мониторинг и защита работающих контейнеров.
    *   **Угрозы:** Атаки на приложение внутри контейнера, попытки "побега" из контейнера, аномальная сетевая активность.
    *   **Контроль:** Мониторинг системных вызовов (Runtime Security), анализ логов, обнаружение вторжений. [4]

## 3. Основные угрозы и векторы атак

### Плохая практика

Запускать контейнер из неизвестного публичного репозитория с флагом `--privileged`. Это равносильно запуску непроверенного бинарного файла с root-правами на вашем сервере.

```bash
# ПЛОХОЙ ПРИМЕР: Никогда так не делайте в production
docker run --rm -it --privileged ubuntu:latest bash
```

### Лучшая практика

Использовать минимальные, проверенные образы и запускать их с минимально необходимыми привилегиями.

```bash
# ХОРОШИЙ ПРИМЕР: Используем официальный, минимальный образ без лишних прав
docker run --rm -it --cap-drop ALL --security-opt no-new-privileges nginx:1.25-alpine
```

### Разбор ключевых угроз

| Угроза | Описание | Пример решения |
| :--- | :--- | :--- |
| **Уязвимые образы** | Использование базовых образов или зависимостей с известными CVE. | Сканирование образов (Trivy, Clair) на этапе CI/CD. [3] |
| **"Побег" из контейнера (Container Escape)** | Эксплуатация уязвимостей ядра Linux для получения доступа к хост-системе. | Использование gVisor, Kata Containers; запуск без root; AppArmor/Seccomp. |
| **Небезопасная конфигурация демона Docker** | Открытый Docker API, позволяющий любому создавать контейнеры. | Настройка TLS-аутентификации для Docker API, следование CIS Benchmarks. |
| **Неправильная конфигурация оркестратора** | Анонимный доступ к Kubernetes API, избыточные права у ServiceAccounts. | Настройка RBAC, Network Policies, Pod Security Standards. [12] |
| **Встроенные секреты** | Хранение паролей, токенов, API-ключей прямо в образе контейнера или переменных окружения. [5] | Использование систем управления секретами (Vault, Kubernetes Secrets, AWS Secrets Manager). |
| **Атаки на приложение** | Стандартные веб-атаки (SQLi, XSS, RCE), нацеленные на приложение внутри контейнера. | Web Application Firewall (WAF), статический и динамический анализ кода (SAST/DAST). |

### Команды-методички

**Проверить, не открыт ли ваш Docker API всему миру:**

```bash
# Подключитесь к вашему серверу и выполните
curl http://localhost:2375/version

# Если вы получили JSON-ответ, ваш API доступен без аутентификации по HTTP.
# Это серьезная уязвимость.
```

**Посмотреть метаданные безопасности Docker:**

```bash
# Показывает, какие профили AppArmor/Seccomp используются
docker info --format '{{json .SecurityOptions}}'
```
