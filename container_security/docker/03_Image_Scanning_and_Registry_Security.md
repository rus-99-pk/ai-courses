w# Файл 3: Сканирование образов и безопасность репозиториев

Создание "чистого" образа — это только полдела. Далее необходимо убедиться, что в нем нет известных уязвимостей, и безопасно его хранить.

## 1. Сканирование образов на уязвимости (Image Scanning)

**Задача, которую мы решаем:** Автоматическое обнаружение известных уязвимостей (CVE) в пакетах операционной системы (apt, apk) и зависимостях приложений (npm, pip, maven), содержащихся в нашем Docker-образе. [16, 21]

### Инструменты для сканирования

Существует множество как open-source, так и коммерческих сканеров. Для Middle DevOps инженера важно владеть хотя бы одним из популярных open-source инструментов. [3, 9, 20]

| Инструмент | Описание | Преимущества |
| :--- | :--- | :--- |
| **Trivy** | Популярный open-source сканер от Aqua Security. Сканирует ОС пакеты, зависимости приложений, IaC-файлы. [19, 23, 25] | Очень прост в использовании, быстрый, имеет множество форматов вывода, легко встраивается в CI/CD. |
| **Grype** | Open-source сканер от Anchore. Схож с Trivy по функциональности. | Легковесный, прост в настройке. |
| **Clair** | Open-source сканер от Quay (Red Hat). Часто используется как "движок" для сканирования в различных системах. [5, 7, 12] | Мощный, расширяемый, спроектирован для интеграции с реестрами образов. [17] |
| **Docker Scout** | Встроенный в экосистему Docker инструмент (ранее Docker Scan). [3] | Нативная интеграция с Docker Hub и Docker Desktop. [14] |

### Практический пример: Сканирование с помощью Trivy

**Trivy** — отличный выбор для начала благодаря своей простоте и эффективности. [4]

#### Установка Trivy
Инструкции по установке можно найти на официальной странице GitHub. Для большинства систем это просто скачивание бинарного файла или использование пакетного менеджера.

#### Команды-методички (Trivy)

**1. Простое сканирование образа:**
Эта команда скачает последнюю базу уязвимостей и выведет отчет в виде таблицы.

```bash
# Сканируем образ по его имени и тегу
trivy image python:3.9-alpine
```

**2. Фильтрация по уровню опасности:**
В CI/CD пайплайне часто необходимо "уронить" сборку, если найдены критические уязвимости.

```bash
# Показать только HIGH и CRITICAL уязвимости
trivy image --severity HIGH,CRITICAL my-app:1.0

# "Уронить" пайплайн, если найдены уязвимости указанной или большей серьезности
# --exit-code 1 говорит Trivy вернуть ненулевой код выхода в случае нахождения уязвимостей
trivy image --exit-code 1 --severity CRITICAL my-app:1.0
```

**3. Различные форматы вывода:**
Для интеграции с другими системами (например, DefectDojo) или для генерации отчетов можно использовать разные форматы.

```bash
# Вывод в формате JSON
trivy image --format json -o report.json my-app:1.0

# Создание CycloneDX Software Bill of Materials (SBOM)
trivy image --format cyclonedx -o sbom.json my-app:1.0
```

**4. Интеграция в CI/CD (Пример для GitLab CI):**
Сканирование должно быть обязательным шагом в вашем пайплайне после сборки образа.

```yaml
# .gitlab-ci.yml
stages:
  - build
  - test

build_image:
  stage: build
  script:
    - docker build -t $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA .
    - docker push $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA

scan_image:
  stage: test
  image:
    name: aquasec/trivy:latest
    entrypoint: [""]
  script:
    # Переопределяем entrypoint, чтобы можно было выполнить команду
    # Указываем, чтобы Trivy не обновлял базу данных каждый раз (--skip-db-update)
    # и использовал кеш для ускорения
    - trivy image --exit-code 0 --format table $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA
    # Отдельная "провальная" проверка для блокировки merge request
    - trivy image --exit-code 1 --severity CRITICAL $CI_REGISTRY_IMAGE:$CI_COMMIT_SHA
```

## 2. Безопасность репозитория образов (Registry Security)

Репозиторий (Registry) — это место, где хранятся ваши "золотые" образы. Его компрометация может привести к внедрению вредоносного кода во все ваши приложения.

**Задачи, которые мы решаем:**

*   **Контроль доступа:** Гарантировать, что только авторизованные пользователи и системы могут загружать (push) и скачивать (pull) образы. [18, 21]
*   **Целостность образов:** Обеспечить, чтобы образ, который мы загрузили, был тем же самым, что мы скачиваем, без каких-либо изменений. [18]
*   **Изоляция и шифрование:** Защита репозитория от сетевых атак и обеспечение шифрования при передаче данных. [10]

### Лучшие практики

1.  **Используйте приватные репозитории:** Никогда не храните образы с коммерческим или чувствительным кодом в публичных репозиториях, таких как Docker Hub. Используйте приватные репозитории Docker Hub, Harbor, GitLab Container Registry, AWS ECR, GCP Artifact Registry и т.д.

2.  **Настройте Role-Based Access Control (RBAC):** Применяйте принцип наименьших привилегий. [21] CI/CD системе нужны права на push и pull, production-среде — только на pull. Разработчикам для локального тестирования — тоже только pull.

3.  **Используйте шифрование (TLS):** Весь трафик между Docker-клиентом и репозиторием должен быть зашифрован с помощью TLS, чтобы предотвратить атаки "человек-посередине". [10]

4.  **Включите сканирование в репозитории:** Многие современные репозитории (GitLab, Harbor, ECR, GCR) имеют встроенные сканеры уязвимостей, которые автоматически проверяют образы при загрузке. [18]

## 3. Подпись образов (Image Signing) с Docker Content Trust (DCT)

**Задача, которую мы решаем:** Криптографически гарантировать, что автор образа — именно тот, за кого себя выдает, и что образ не был изменен с момента его подписи. [16]

Docker Content Trust (DCT) построен на базе проекта **Notary**. Он использует набор криптографических ключей для подписи тегов образов. [6, 13]

### Как это работает?

Когда DCT включен, `docker push` не просто загружает образ, но и подписывает его с помощью вашего ключа. `docker pull` перед скачиванием образа сначала проверяет его подпись. Если подпись неверна или отсутствует, `pull` завершится с ошибкой. [2]

### Команды-методички (Docker Content Trust)

**1. Включить DCT на стороне клиента:**
Для включения проверки подписей при скачивании образов, установите переменную окружения.

```bash
# Включить DCT
export DOCKER_CONTENT_TRUST=1
```

**2. Попытка скачать неподписанный образ:**
Если вы попробуете скачать образ, у которого нет подписанного тега (например, `latest`), вы получите ошибку.

```bash
docker pull alpine:latest
# Ожидаемый результат:
# Error: remote trust data does not exist for docker.io/library/alpine: this image does not have trust data for latest
```

**3. Скачивание подписанного образа:**
Большинство официальных образов не имеют подписанного тега `latest`. Чтобы проверить работу DCT, нужно использовать конкретный тег, который был подписан. (На практике найти такие образы на Docker Hub становится все сложнее, так как индустрия движется к другим решениям, например, Sigstore/cosign).

**4. Подпись и загрузка собственного образа:**
При первом `docker push` с включенным DCT вам будет предложено создать корневой ключ (root key) и ключ репозитория (repository key) и защитить их паролями.

```bash
# Включаем DCT для push
export DOCKER_CONTENT_TRUST=1

# Собираем и тегируем наш образ
docker build -t your-dockerhub-username/my-secure-app:1.0 .

# При первом пуше будут сгенерированы ключи
docker push your-dockerhub-username/my-secure-app:1.0
```
> **Нюанс:** Управление ключами DCT вручную может быть сложным, особенно в автоматизированных CI/CD системах. [11] Необходимо безопасно хранить корневой ключ и предоставлять CI/CD системе доступ к ключу репозитория. Из-за этой сложности многие компании используют альтернативы, такие как `cosign` от проекта Sigstore.
