# Файл 2: Безопасность Dockerfile и образов

## 1. Задачи и угрозы на этапе сборки

Безопасность начинается с `Dockerfile`. Этот файл — чертеж вашего контейнера, и ошибки, допущенные здесь, будут размножены в каждом экземпляре вашего приложения. [2]

**Ключевые задачи, которые мы решаем:**

*   **Минимизация поверхности атаки:** Уменьшение количества пакетов, библиотек и инструментов в финальном образе, чтобы сократить число потенциальных уязвимостей. [2, 5]
*   **Предотвращение утечки секретов:** Исключение попадания паролей, токенов и ключей в слои образа. [6, 10, 17]
*   **Обеспечение воспроизводимости сборок:** Гарантия того, что сборка сегодня и через месяц даст идентичный и предсказуемый результат. [10]
*   **Снижение привилегий:** Создание и запуск приложений от имени непривилегированного пользователя внутри контейнера. [18, 19]

## 2. Лучшие практики написания безопасных Dockerfile

### 2.1. Используйте минимальные и доверенные базовые образы

**Плохая практика:** Использовать полный дистрибутив ОС, когда это не требуется.

```dockerfile
# ПЛОХО: ubuntu:22.04 содержит массу ненужных утилит (bash, curl, apt и т.д.)
FROM ubuntu:22.04
# ...
```

**Лучшая практика:** Использовать `alpine`, `slim` или `distroless` образы. [10, 18]

*   **Alpine:** Очень маленький дистрибутив Linux, основанный на musl libc и busybox. Идеален для уменьшения размера образа.
*   **Slim:** Урезанная версия стандартного образа (например, `python:3.11-slim`), которая не включает общие пакеты, ненужные для запуска приложения.
*   **Distroless (от Google):** Содержат только ваше приложение и его runtime-зависимости. В них нет пакетных менеджеров, shell и других утилит. Это значительно усложняет жизнь атакующему, даже если он получит исполнение кода в контейнере.

```dockerfile
# ХОРОШО: Минимальный образ
FROM python:3.11-slim

# ЛУЧШЕ: Distroless образ для Go
FROM gcr.io/distroless/static-debian11
COPY --from=builder /app/myapplication /
CMD ["/myapplication"]
```

### 2.2. Фиксируйте версии (Pinning)

**Плохая практика:** Использовать тег `:latest`. Он непредсказуем и может привести к поломке сборки или появлению новых уязвимостей. [1]

```dockerfile
# ПЛОХO: `latest` может измениться в любой момент
FROM nginx:latest
```

**Лучшая практика:** Использовать конкретные теги версий или, для максимальной безопасности и воспроизводимости, хэш-сумму (digest). [10, 20]

```dockerfile
# ХОРОШО: Фиксация конкретной версии
FROM nginx:1.25.3-alpine

# ЛУЧШЕ: Фиксация по дайджесту для гарантии неизменности
FROM nginx:1.25.3-alpine@sha256:10b8cc432d56da8b61b070f4c7d2543a9ed17c2b23010b43af434fd40e2ca4aa
```

### 2.3. Запускайте процессы от имени непривилегированного пользователя (non-root)

**Плохая практика:** Оставлять пользователя `root` по умолчанию. Если злоумышленник скомпрометирует ваше приложение, он получит root-права внутри контейнера. [10]

**Лучшая практика:** Создать специального пользователя и группу для вашего приложения и переключиться на него с помощью инструкции `USER`. [18]

```dockerfile
FROM alpine:3.18

# Создаем группу и пользователя
RUN addgroup -S appgroup && adduser -S appuser -G appgroup

# Переключаемся на созданного пользователя
USER appuser

# ... дальнейшие инструкции ...```

### 2.4. Используйте многоэтапные сборки (Multi-stage builds)

Это одна из самых важных техник для уменьшения поверхности атаки. Она позволяет использовать один контейнер со всеми инструментами для сборки (компилятор, SDK, `npm install` с `devDependencies`), а затем скопировать только финальный артефакт (бинарный файл, JS-бандл) в чистый, минимальный образ для production. [4, 8, 9, 12]

**Пример задачи:** Собрать Go-приложение.

**Плохая практика (одноэтапная сборка):**

```dockerfile
# ПЛОХО: В финальном образе остается весь Go SDK и исходный код
FROM golang:1.21

WORKDIR /app
COPY . .

# Компилируем приложение
RUN go build -o myapp .

CMD ["./myapp"]
```
*Размер такого образа может быть > 1 ГБ.*

**Лучшая практика (многоэтапная сборка):**

```dockerfile
# --- Этап 1: Сборщик (Builder) ---
FROM golang:1.21-alpine AS builder

WORKDIR /app
COPY . .

# Собираем статически скомпилированный бинарник
RUN CGO_ENABLED=0 go build -ldflags="-w -s" -o myapp .

# --- Этап 2: Финальный образ (Final) ---
# scratch - это абсолютно пустой образ
FROM scratch

# Копируем только скомпилированный бинарник из этапа 'builder'
COPY --from=builder /app/myapp /myapp

# Запускаем приложение
CMD ["/myapp"]
```
*Размер финального образа будет всего несколько мегабайт!*

## 3. Управление секретами во время сборки

**Категорически плохая практика:** Копировать секреты или передавать их через `ARG` / `ENV`. Они навсегда останутся в слоях образа. [6, 10, 14]

```dockerfile
# УЖАСНО: Никогда так не делайте
ENV API_KEY=supersecretkey123
ARG NPM_TOKEN=anothersecret
COPY config.json .
```

**Лучшая практика:** Использовать `docker build --secret` (требуется BuildKit). Это монтирует секрет как временный файл в контейнер на время выполнения одной `RUN` команды и не сохраняет его в слоях. [7, 11, 13]

**Пример: Установка приватных NPM-пакетов**

1.  Создайте файл `.npmrc` с вашим токеном:
    ```
    //registry.npmjs.org/:_authToken=${NPM_TOKEN}
    ```

2.  Обновите `Dockerfile`:

    ```dockerfile
    # syntax=docker/dockerfile:1
    FROM node:18-alpine

    WORKDIR /app
    COPY package*.json ./

    # Монтируем секрет .npmrc только на время выполнения npm ci
    RUN --mount=type=secret,id=npmrc,target=/root/.npmrc npm ci

    COPY . .
    CMD ["node", "index.js"]
    ```

3.  Выполните сборку с передачей секрета:

    ```bash
    # Включаем BuildKit и передаем секрет
    DOCKER_BUILDKIT=1 docker build --secret id=npmrc,src=.npmrc -t my-secure-app .
    ```

## 4. Команды-методички

**Посмотреть историю и слои образа, чтобы найти "запеченные" секреты:**

```bash
docker history my-app-image

# Ищите команды, которые могли скопировать или создать файлы с секретами
```

**Использовать `.dockerignore`:**

Создайте файл `.dockerignore` в корне проекта (синтаксис как у `.gitignore`), чтобы предотвратить случайное копирование секретов, локальных конфигураций или папки `.git` в образ.

```.dockerignore
.git
.env
*.pem
aws-credentials.json
Dockerfile
README.md
```

**Включить BuildKit для доступа к современным функциям:**

```bash
# Установить как переменную окружения для текущей сессии
export DOCKER_BUILDKIT=1

# Или включить по умолчанию в конфигурации демона /etc/docker/daemon.json
{
  "features": {
    "buildkit": true
  }
}
```
