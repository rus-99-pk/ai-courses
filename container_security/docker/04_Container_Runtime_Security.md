# Файл 4: Безопасность среды выполнения (Runtime Security)

Даже идеально собранный и проверенный образ может быть скомпрометирован во время выполнения из-за уязвимостей в приложении или неверной конфигурации. Runtime Security фокусируется на защите контейнеров "в бою".

**Задачи, которые мы решаем:**

*   **Изоляция и ограничение ущерба:** Предотвращение "побега" из контейнера (container escape) и ограничения влияния скомпрометированного контейнера на хост и другие контейнеры. [1]
*   **Принцип наименьших привилегий:** Ограничение прав и возможностей контейнера только теми, которые абсолютно необходимы для его работы. [2, 4]
*   **Обнаружение угроз в реальном времени:** Мониторинг поведения контейнеров для выявления аномальной активности, такой как запуск shell, изменение бинарных файлов или подозрительные сетевые подключения. [3]
*   **Предотвращение атак на исчерпание ресурсов (DoS):** Ограничение потребления CPU и памяти для каждого контейнера. [2, 10]

## 1. Изоляция на уровне ядра: Linux Capabilities, Seccomp, AppArmor

Docker использует встроенные в ядро Linux механизмы для изоляции контейнеров. Понимание и правильная настройка этих механизмов — ключевой навык для DevOps инженера.

### 1.1. Linux Capabilities

Вместо того чтобы давать процессу полные права `root`, capabilities разбивают их на более чем 30 мелких привилегий (например, `CAP_NET_BIND_SERVICE` для открытия портов ниже 1024, `CAP_CHOWN` для смены владельца файла). [24]

**Плохая практика:** Запускать контейнер с флагом `--privileged`. Это отключает все механизмы изоляции и дает контейнеру полный `root` доступ к хосту. **Никогда не используйте это в production.**

**Лучшая практика:** Следовать принципу наименьших привилегий. По умолчанию Docker уже отключает большинство опасных capabilities. Ваша задача — отключать еще больше, если они не нужны. [21, 23]

```bash
# ПЛОХО: Полный доступ к хосту
docker run -d --privileged nginx

# ХОРОШО: Отключаем ВСЕ capabilities, а затем добавляем только необходимые.
# В данном случае для nginx не требуется никаких специальных прав.
docker run -d --cap-drop ALL --cap-add NET_BIND_SERVICE nginx
```

**Нюанс:** Для большинства веб-приложений, которые не требуют специальных системных привилегий, лучшей практикой является отключение всех capabilities (`--cap-drop ALL`).

### 1.2. Seccomp (Secure Computing Mode)

Seccomp — это фильтр системных вызовов (syscalls) ядра Linux. [14, 16] Он действует как файрвол, разрешая или запрещая контейнеру обращаться к ядру с определенными запросами. По умолчанию Docker использует профиль, который блокирует около 44 из 300+ системных вызовов, известных как опасные. [24]

**Лучшая практика:** В большинстве случаев стандартного профиля seccomp достаточно. Для сред с повышенными требованиями к безопасности можно создать собственный, более строгий JSON-профиль и применить его.

```bash
# Запуск контейнера с кастомным профилем seccomp
docker run --rm -it --security-opt seccomp=/path/to/profile.json alpine sh
```
Запрет таких вызовов, как `ptrace`, значительно усложняет эксплуатацию уязвимостей ядра. [17]

### 1.3. AppArmor (Application Armor)

AppArmor — это модуль безопасности ядра, который позволяет ограничивать возможности программ с помощью профилей. [20] В отличие от seccomp, который фильтрует syscalls, AppArmor работает на уровне доступа к файловой системе, сети и capabilities. [16, 17] Docker по умолчанию использует профиль `docker-default`. [22]

**Лучшая практика:** Как и с seccomp, для большинства приложений стандартного профиля достаточно. Однако вы можете создать собственный профиль, чтобы, например, запретить приложению запись в определенные директории.

```bash
# Загружаем кастомный профиль в AppArmor
sudo apparmor_parser -r -W /path/to/custom-profile

# Запускаем контейнер с этим профилем
docker run --rm -it --security-opt apparmor=custom-profile-name alpine sh
```

## 2. Дополнительные флаги безопасности

### `no-new-privileges`
Этот флаг запрещает дочерним процессам внутри контейнера получать больше привилегий, чем у родительского процесса, например, через `setuid` или `setgid` биты. Это важная мера против атак повышения привилегий. [11, 21, 23]

```bash
# РЕКОМЕНДУЕТСЯ: Запрещаем эскалацию привилегий
docker run --rm -it --security-opt no-new-privileges alpine sh
```

### `read-only` файловая система
Запуск контейнера с read-only корневой файловой системой значительно снижает риски. Атакующий не сможет изменить бинарные файлы, конфигурацию или записать вредоносный скрипт.

```bash
# Запускаем контейнер с файловой системой только для чтения
# Для директорий, куда приложению действительно нужна запись (логи, временные файлы),
# монтируем временные файловые системы (tmpfs)
docker run -d --read-only --tmpfs /run --tmpfs /tmp nginx
```

## 3. Ограничение ресурсов

Ограничение ресурсов — это мера не только производительности, но и безопасности. [18] Контейнер с уязвимостью (например, "утечкой" памяти) или скомпрометированный контейнер, запущенный для майнинга криптовалют, может исчерпать все ресурсы хоста, вызывая отказ в обслуживании (DoS) для всех остальных контейнеров. [10, 12, 19]

**Команды-методички:**

```bash
docker run -d \
  # Ограничить использование памяти до 1 ГБ
  --memory="1g" \
  # Установить мягкий лимит. Контейнер будет использовать его, когда нет нехватки памяти
  --memory-reservation="750m" \
  # Ограничить использование CPU до половины одного ядра
  --cpus="0.5" \
  nginx
```

## 4. Мониторинг угроз в реальном времени с помощью Falco

**Задача, которую мы решаем:** Обнаружение подозрительной активности внутри работающих контейнеров в реальном времени.

**Falco** — это open-source проект CNCF, который стал стандартом де-факто для runtime security. [5, 8] Он подключается к ядру Linux (через eBPF или модуль ядра) и отслеживает системные вызовы, сравнивая их с набором правил. [7]

**Примеры того, что может обнаружить Falco:**

*   Запуск shell (`bash`, `sh`) в контейнере.
*   Запись в `/etc`, `/bin`, `/usr/bin` и другие системные директории.
*   Открытие исходящего сетевого соединения процессом, который не должен этого делать.
*   Чтение чувствительных файлов, таких как `/etc/shadow`.
*   Запуск инструментов для сбора информации (`tcpdump`, `strace`).

### Пример правила Falco:

```yaml
- rule: Shell spawned in a container
  desc: A shell was spawned in a container with an attached terminal.
  condition: >
    evt.type = execve and evt.dir = < and container.id != host and
    proc.name in (shell_binaries) and proc.tty != 0
  output: >
    Shell spawned in a container (user=%user.name container_id=%container.id
    container_name=%container.name image=%container.image.repository
    shell=%proc.name parent=%proc.pname cmdline=%proc.cmdline)
  priority: WARNING
```

### Как начать работать с Falco?

Falco обычно устанавливается как DaemonSet в Kubernetes, чтобы он работал на каждой ноде кластера. [9] Его алерты можно направлять в Slack, SIEM-системы или другие инструменты мониторинга через Falcosidekick. [15]

**Команды-методички:**

```bash
# После установки Falco, посмотреть его логи/алерты
journalctl -fu falco

# Запустить shell в любом контейнере на хосте
docker exec -it <container-id> /bin/bash

# Вы увидите алерт от Falco в логах, сообщающий о запуске shell.
```
