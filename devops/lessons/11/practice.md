Отлично! Вот мы и подошли к самому важному этапу курса — объединению всех полученных знаний в единый, работающий конвейер. Итоговый проект — это ваша возможность не только закрепить материал, но и создать реальный пример ваших навыков, который можно будет показать потенциальным работодателям.

Это не просто набор изолированных задач, а комплексная система. Подходите к нему как к мини-проекту в реальной компании.

**УРОК 11: ИТОГОВЫЙ ПРОЕКТ (3 НЕДЕЛИ)**

**Общая Цель:** Построить полный, автоматизированный конвейер DevOps для выбранного веб-приложения, охватывающий все этапы от коммита кода до работающего, наблюдаемого приложения в Kubernetes.

**Ожидаемый Результат:** Набор Git репозиториев (код приложения, инфраструктура/манифесты K8s), работающий CI/CD пайплайн (в Jenkins или GitLab CI), развернутая инфраструктура (K8s кластер, БД, Vault), задеплоенное приложение в K8s, настроенные мониторинг и логирование, базовый документ с описанием проекта.

**Рекомендуемый Подход:** Итеративный. Не пытайтесь сделать все идеально с первого раза. Двигайтесь по этапам, добиваясь работоспособности на каждом шаге. Используйте как справочник методички к предыдущим урокам.

**Выбор Приложения:**

*   Возьмите то же самое Java приложение, над которым работали в Labs. Оно уже имеет базу для подключения к БД и, возможно, внешнюю зависимость (например, вызов стороннего API, работа с файлами, которые можно хранить в S3/MinIO).
*   Или выберите другое простое веб-приложение на любом языке, с которым знакомы (Python/Flask/Django, Node.js/Express, Go и т.д.). Главное, чтобы у него были:
    *   Исходный код, управляемый системой сборки (Maven, Gradle, pip, npm, Go modules).
    *   Unit-тесты.
    *   Интеграция с реляционной БД (PostgreSQL предпочтительно, т.к. освоили Flyway).
    *   Потенциально, зависимость от внешнего хранилища (файлы, S3 API).
    *   Предоставление метрик (например, в формате Prometheus).
    *   Логирование в stdout/stderr.
    *   Получение конфигурации (в т.ч. секретов) из переменных окружения.

**Структура Проекта:**

Рекомендуется использовать несколько Git репозиториев для чистоты и разделения ответственности:

1.  `app-code-repo`: Исходный код приложения, Dockerfile, Flyway миграции, Jenkinsfile / `.gitlab-ci.yml` (для части CI).
2.  `infra-code-repo`: Terraform код для Provisioning инфраструктуры (VM, K8s кластер). Ansible Playbooks для настройки VM. DBOps скрипты (если не в Flyway).
3.  `k8s-manifests-repo`: Helm Chart приложения, K8s манифесты для Vault, Monitoring, Ingress. Это репозиторий, который будет отслеживать Argo CD.

(Можно объединить 2 и 3, или 1 и 3, но разделение на 3 репозитория хорошо соответствует реальным сценариям).

**ПЛАН ПО НЕДЕЛЯМ:**

**Неделя 1: Основы CI и Управление Артефактами**

*   **Цель:** Настроить базовый CI пайплайн, который собирает приложение, тестирует, анализирует, собирает Docker образ и публикует его.
*   **Задачи:**
    1.  **Setup Repositories:** Создайте 3 (или выбранное количество) репозиториев в вашем Gitea/GitLab для нового проекта (e.g., `my-devops-project-app`, `my-devops-project-infra`, `my-devops-project-k8s`).
    2.  **Initial App Code:** Поместите исходный код выбранного приложения в `app-code-repo`. Добавьте систему сборки (Maven/Gradle/npm/pip etc.) и Unit тесты.
    3.  **Dockerfile:** Напишите Dockerfile для вашего приложения (Урок 7, Lab 1). Убедитесь, что он собирает приложение и готов к запуску.
    4.  **Container Registry:** Убедитесь, что у вас есть доступный Docker Container Registry (Nexus, GitLab Registry, Docker Hub).
    5.  **Artifact Repository:** Убедитесь, что у вас есть доступный Maven/Generic Repository (Nexus) для публикации других артефактов.
    6.  **SonarQube:** Убедитесь, что SonarQube запущен и доступен. Создайте новый проект в SonarQube для вашего приложения. Получите токен.
    7.  **CI Pipeline (Часть 1 - Build & Publish):**
        *   Выберите вашу CI систему (Jenkins или GitLab CI). Убедитесь, что она настроена и имеет необходимые инструменты (Java/Node/Python, Maven/Gradle/npm/pip, Docker, SonarQube Scanner CLI) или может их использовать (через Docker in Docker, например).
        *   Создайте Jenkins Job (тип Pipeline) или `.gitlab-ci.yml` в `app-code-repo`.
        *   Настройте Source Code Management (клонирование `app-code-repo`).
        *   Добавьте этапы (Stages) в пайплайн:
            *   `Checkout` (клонирование кода - часто автоматически).
            *   `Build`: Сборка приложения (e.g., `mvn clean package`).
            *   `Unit Tests`: Запуск юнит-тестов. Публикация отчетов о тестах (e.g., JUnit).
            *   `Code Analysis`: Запуск анализа SonarQube (e.g., `mvn sonar:sonar` или SonarScanner CLI). Убедитесь, что токен SonarQube используется безопасно (через Credential/CI Variable).
            *   `Quality Gate Check`: Проверка Quality Gate в SonarQube. Сборка должна падать, если Quality Gate не пройден (Урок 2, Lab 3).
            *   `Publish Maven Artifact` (опционально, если собираете JAR/WAR): Публикация артефакта в Nexus (Урок 4, Lab 2). Убедитесь, что Credential для Nexus используется безопасно.
            *   `Build Docker Image`: Сборка Docker образа из Dockerfile (Урок 7, Lab 1).
            *   `Tag Docker Image`: Пометка образа тегом (например, с номером сборки CI, хешем коммита, или версией приложения из pom.xml).
            *   `Publish Docker Image`: Публикация Docker образа в Container Registry (Урок 7, Lab 2). Убедитесь, что Credential для Registry используется безопасно.
        *   Настройте триггер CI (webhook) для запуска пайплайна при коммите в ветку `develop` (или `main`) в `app-code-repo`.
    8.  **Тестирование CI:** Сделайте несколько коммитов в `app-code-repo`. Убедитесь, что пайплайн запускается автоматически, все этапы выполняются успешно, артефакты (JAR/WAR, Docker Image) публикуются, и анализ SonarQube проходит. Попробуйте внести ошибку или нарушение Quality Gate, чтобы увидеть, что сборка падает.

**Результат Недели 1:** Автоматизированный CI пайплайн, который превращает исходный код в готовые к деплою артефакты и проверяет их качество/безопасность.

**Неделя 2: Инфраструктура, Базы Данных и Секреты**

*   **Цель:** Автоматизировать создание и настройку окружения (K8s кластер, БД, Vault) и интегрировать управление изменениями БД и секретами.
*   **Задачи:**
    1.  **Infra as Code (Terraform):**
        *   В `infra-code-repo`, напишите Terraform код для Provisioning Staging окружения. Это может включать:
            *   Kubernetes кластер (Minikube/Kind для простоты, или Managed K8s в облаке).
            *   VM для базы данных (если не в K8s).
            *   VM для Vault (если не в K8s).
            *   VM для Jenkins/Runner/SonarQube/Nexus/Grafana/Prometheus/Alertmanager, если вы решили полностью пересоздавать всю инфраструктуру (сложнее!). Проще использовать существующие сервисы и Provision'ить только таргет-окружение (K8s/DB/Vault).
        *   Настройте Remote State для Terraform (Урок 5, Lab 2).
        *   Настройте аутентификацию Terraform для вашего провайдера (облако/гипервизор) на Jenkins/Runner VM (Урок 5, Техническая подготовка). Убедитесь, что учетные данные используются безопасно (через Credential/CI Variable).
    2.  **Configuration Management (Ansible):**
        *   В `infra-code-repo`, напишите Ansible Playbooks для:
            *   Настройки DB VM: Установка СУБД (PostgreSQL/MongoDB), создание пользователя и базы данных для приложения.
            *   Настройки Vault VM: Установка Vault (если не в Docker), базовая настройка.
            *   Установки Docker на нодах K8s (если не Managed K8s).
            *   Установки `kubectl`, Helm, Argo CD CLI на Jenkins/Runner VM, если они еще не установлены или нужно обеспечить конкретные версии.
        *   Настройте Inventory Ansible.
        *   Настройте SSH доступ по ключу с Jenkins/Runner VM к новым VM (DB VM, Vault VM), созданным Terraform (Урок 3, Lab 4).
    3.  **DBOps (Flyway/Liquibase):**
        *   В `app-code-repo` или `infra-code-repo`, убедитесь, что Flyway/Liquibase интегрирован в проект и есть скрипты миграций (Урок 6, Lab 4).
        *   Добавьте в ваш CI/CD пайплайн (в `app-code-repo`) новый этап *перед* этапом деплоя:
            *   `Database Migrations`: Запустить Flyway/Liquibase Apply на целевой базе данных (на DB VM). Убедитесь, что учетные данные к БД используются безопасно (из Vault или через Credential/CI Variable).
    4.  **Secrets Management (Vault):**
        *   Убедитесь, что Vault развернут и настроен (через Terraform/Ansible или вручную для этой Lab).
        *   Настройте KV Secret Engine в Vault. Запишите туда секреты вашего приложения (учетные данные к БД, API ключи, т.д.) (Урок 7, Lab 6).
        *   Интегрируйте приложение с Vault. Либо измените код приложения, либо используйте скрипт-обертку (Урок 7, Lab 7). Убедитесь, что Vault токен используется безопасно (не хардкодится, передается через переменную окружения из K8s Secret или Vault Agent).
    5.  **CI/CD Pipeline (Часть 2 - Infra & DB):**
        *   Обновите Jenkinsfile / `.gitlab-ci.yml` в `app-code-repo`.
        *   Добавьте этапы *перед* этапами сборки Docker образа и публикации:
            *   `Clone Infra Code`: Склонировать `infra-code-repo`.
            *   `Provision Infrastructure`: Запустить Terraform ( `terraform init`, `terraform apply -auto-approve`).
            *   `Wait for Infrastructure`: Подождать, пока VM станут доступны по SSH.
            *   `Configure Infrastructure`: Запустить Ansible Playbooks.
            *   `Database Migrations`: Запустить миграции БД (как описано в шаге 3 этой недели).
        *   **Важно:** Теперь пайплайн должен сначала подготовить окружение, а затем собрать и опубликовать артефакты. Этапы деплоя пока остаются неполными или будут переделаны в Неделе 3.
    6.  **Тестирование Infra & DB Stages:** Запустите полный пайплайн. Проверьте логи. Убедитесь, что Terraform создает VM, Ansible их настраивает, Flyway применяет миграции. Проверьте состояние VM и БД вручную после выполнения пайплайна.

**Результат Недели 2:** Автоматизированный процесс подготовки окружения (инфраструктура и база данных) и применения миграций БД как часть пайплайна. Секреты хранятся в Vault.

**Неделя 3: Оркестрация (Kubernetes), GitOps и Наблюдаемость**

*   **Цель:** Развернуть приложение в Kubernetes, управляемом через GitOps, и настроить полный стек наблюдаемости.
*   **Задачи:**
    1.  **Kubernetes Cluster:** Убедитесь, что ваш K8s кластер создан (с помощью Terraform в Неделе 2 или вручную/Minikube/Kind для этой Lab).
    2.  **Container Registry & Nexus:** Убедитесь, что Docker Image и Maven/другие артефакты публикуются (из Недели 1).
    3.  **K8s Manifests (Repo & Helm Chart):**
        *   В `k8s-manifests-repo`, создайте Helm Chart для вашего приложения (Урок 9, Lab 7).
        *   В Chart'е:
            *   Определите Deployment для вашего приложения, использующий образ из Container Registry.
            *   Настройте Service для доступа к приложению (NodePort/LoadBalancer/ClusterIP + Ingress).
            *   Используйте ConfigMaps и Secrets (или интеграцию с Vault) для конфигурации и секретов приложения в K8s (Урок 9, Lab 5).
            *   Определите PersistentVolumeClaim, если приложению нужно персистентное хранилище.
            *   Добавьте liveness и readiness probes.
            *   Настройте ресурсы (CPU/Memory requests/limits).
            *   Добавьте аннотации для Service Discovery Prometheus (Урок 10, Lab 4).
        *   Проверьте Chart локально (`helm template`, `helm lint`).
    4.  **GitOps (Argo CD):**
        *   Установите Argo CD в ваш K8s кластер (Урок 9, Lab 8).
        *   Настройте Argo CD для отслеживания ветки (`main` или `develop`) в `k8s-manifests-repo` и деплоя вашего Helm Chart'а в нужный неймспейс K8s (Урок 9, Lab 8).
        *   Настройте автоматическую синхронизацию в Argo CD.
        *   **Optional Promotion:** Если хотите иметь ручное подтверждение (как в Уроке 4), настройте ручную синхронизацию в Argo CD или используйте функционал AppProject/Promotion в Argo CD.
    5.  **CI/CD Pipeline (Часть 3 - GitOps Trigger):**
        *   Удалите или отключите старые этапы деплоя на Staging/Prod из Jenkinsfile / `.gitlab-ci.yml` в `app-code-repo`.
        *   Обновите этап `Update K8s Manifests` (из Недели 2) так, чтобы он обновлял тег образа в `values.yaml` вашего Helm Chart'а в `k8s-manifests-repo` после успешной сборки и публикации Docker образа (Урок 9, Lab 9).
    6.  **Observability Stack:**
        *   Установите стек мониторинга и логирования (Prometheus, Grafana, Loki, Alertmanager) в K8s кластер (Урок 10, Lab 1 & 2) или убедитесь, что ваши внешние сервисы настроены на сбор данных из этого кластера.
        *   Настройте Promtail/лог-агент для сбора логов с Pods приложения и отправки в Loki (Урок 10, Lab 3).
        *   Настройте Prometheus для скрапинга метрик с Pods приложения (Урок 10, Lab 4). Убедитесь, что приложение предоставляет метрики (например, через Actuator).
        *   Настройте Grafana Data Sources для Loki и Prometheus. Создайте дашборды для логов и метрик вашего приложения (Урок 10, Lab 3 & 5).
        *   Настройте правила алертинга в Prometheus и Alertmanager для вашего приложения (например, падение Pod, высокая задержка, ошибки) (Урок 10, Lab 6). Настройте приемник уведомлений (например, в файл или тестовый канал).
    7.  **Rollback:** Опишите процесс отката на предыдущую версию. Это может включать:
        *   Откат Helm релиза (`helm rollback <release-name> <revision>`).
        *   Откат Deployment в K8s (`kubectl rollout undo deployment/<deployment-name>`).
        *   Откат миграций БД (если Flyway/Liquibase скрипты для отката написаны).
        *   Как Argo CD поддерживает откат (синхронизация с предыдущим коммитом в Git).
    8.  **Documentation:** Напишите файл `README.md` в корне `app-code-repo` (или отдельный документ) с описанием проекта. Включите:
        *   Обзор приложения и его архитектуры (если микросервисы).
        *   Обзор DevOps конвейера: какие инструменты используются на каждом этапе (CI, IaC, CM, DBOps, K8s, GitOps, Monitoring), как они взаимодействуют. Можно использовать диаграмму.
        *   Как запустить проект (инструкции по развертыванию инфраструктуры, установке вспомогательных сервисов, первоначальному деплою приложения).
        *   Как выполнить деплой новой версии (сделать коммит в `app-code-repo`).
        *   Как проверить логи, метрики, алерты.
        *   Как выполнить откат.
        *   Архитектура K8s деплоя (Deployment, Service, ConfigMap, Secret, PVC).
        *   Информация о Vault (где хранятся секреты).
        *   Любые компромиссы или упрощения, сделанные в рамках проекта (например, использование Minikube, файловый Storage Vault, упрощенный скрипт отката).
        *   Предложения по улучшению (что можно сделать в production: HA для всех компонентов, TLS везде, продвинутые стратегии деплоя, Service Mesh, Security Scanning на всех этапах и т.д.).

    9.  **Финальное тестирование:** Сделайте коммит с небольшим изменением в коде приложения. Проверьте, что пайплайн проходит полностью, Argo CD деплоит новую версию в K8s, мониторинг и логирование работают, и вы можете проверить состояние приложения.

**Результат Недели 3:** Полностью работающий DevOps конвейер, задеплоенное в K8s приложение, управляемое через GitOps, полный стек наблюдаемости, и документация, описывающая весь процесс.
