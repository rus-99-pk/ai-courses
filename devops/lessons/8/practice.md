**ТЕОРЕТИЧЕСКИЙ БЛОК (Краткий обзор)**

*   **Архитектурные стили:**
    *   **Монолит:** Все компоненты приложения (UI, бизнес-логика, доступ к данным) собраны в едином блоке кода. Проще разрабатывать и деплоить на старте. Недостатки: сложность масштабирования отдельных частей, долгая сборка, трудность внедрения новых технологий, высокий риск при изменениях ("эффект бабочки").
    *   **Микросервисы:** Приложение разбито на набор небольших, слабосвязанных сервисов, каждый из которых выполняет конкретную бизнес-функцию, имеет свою базу данных (часто) и может быть разработан, развернут и масштабирован независимо от других. Преимущества: масштабирование отдельных сервисов, использование разных технологий, устойчивость к сбоям (сбои одного сервиса не обязательно влияют на другие), ускорение разработки (независимые команды). Недостатки: сложность управления (больше сервисов, больше деплоев), распределенные транзакции, мониторинг, сетевое взаимодействие.

*   **Управление микросервисами:** Требует инструментов для оркестрации (запуск, остановка, масштабирование, самовосстановление), обнаружения сервисов (service discovery), маршрутизации запросов, централизованного логирования и мониторинга. Docker Compose - базовый инструмент для локальной разработки/тестирования мульти-контейнерных приложений. Kubernetes (Урок 9) - промышленный стандарт для оркестрации.

*   **Docker Compose:** Инструмент для определения и запуска мульти-контейнерных приложений в Docker. Конфигурация описывается в файле `docker-compose.yml` (YAML формат). Позволяет определить сервисы (контейнеры), сети и вольюмы, связи между сервисами.

*   **Балансировка нагрузки (Load Balancing):** Распределение входящих сетевых запросов между несколькими экземплярами приложения. Цель: повысить доступность (Availability), надежность (Reliability) и производительность (Performance).
    *   **Алгоритмы:** Round Robin (поочередно), Least Connection (наименьшее количество активных соединений), IP Hash (на основе IP клиента).
    *   **Reverse Proxy:** Сервер, который принимает запросы от клиентов и перенаправляет их на один или несколько серверов приложений. Скрывает топологию внутренней сети. Nginx часто используется как Reverse Proxy.
    *   **Load Balancer:** Может быть отдельным устройством/сервисом (аппаратным или программным), который специализируется на распределении нагрузки. Reverse Proxy может выполнять функцию Load Balancer, когда перенаправляет на несколько серверов.

*   **Кеширование (Caching):** Сохранение копий часто запрашиваемых данных или результатов вычислений во временном хранилище (кеше) для более быстрого доступа в будущем. Улучшает производительность и снижает нагрузку на бэкенд.
    *   **Типы:** Браузерный кеш, CDN (Content Delivery Network), Прокси-кеш (Nginx может кешировать ответы бэкенда), Кеш на стороне приложения (Redis, Memcached).

*   **Стратегии развертывания и балансировщики:**
    *   **Blue/Green:** Балансировщик переключает трафик с "синего" (старой версии) пула серверов на "зеленый" (новой версии) пул. Требует поддержки со стороны балансировщика (например, переключение пулов бэкендов).
    *   **Canary:** Балансировщик направляет небольшой процент трафика на новую версию, остальной трафик - на старую. Если новая версия стабильна, процент трафика постепенно увеличивается. Требует более продвинутых возможностей балансировщика (процентное распределение трафика).

**Lab 3: Настройка Nginx как Reverse Proxy**

*   **Цель:** Настроить Nginx для перенаправления входящих HTTP запросов на ваше приложение, запущенное в Docker контейнере.
*   **Предварительные требования:**
    *   Работающий Nginx (Lab 2).
    *   Ваше приложение запущено в Docker контейнере на *той же* VM, где установлен Nginx, или на *другой* VM, доступной по сети.
    *   Если приложение запущено на другой VM, убедитесь, что Nginx VM может подключиться к порту приложения на Staging VM (файрволы).
*   **Шаги:**

    1.  **Определите, где запущен контейнер с приложением и на каком порту:** Например, на VM с IP `IP_STAGING_VM` на порту 8080.

    2.  **Создайте файл конфигурации Nginx для вашего сайта/приложения:** В Ubuntu/Debian файлы конфигурации для отдельных сайтов обычно хранятся в `/etc/nginx/sites-available/` и активируются созданием символической ссылки в `/etc/nginx/sites-enabled/`.
        ```bash
        # На Nginx VM
        sudo nano /etc/nginx/sites-available/my-app.conf
        ```
    3.  **Добавьте следующую конфигурацию:**

        ```nginx
        # /etc/nginx/sites-available/my-app.conf

        server {
            listen 80; # Nginx слушает на 80 порту
            server_name ВАШ_IP_VM_NGINX или ВАШ_ДОМЕН; # Имя сервера (IP или домен, по которому обращаются к Nginx)

            location / {
                # Перенаправляем все запросы на бэкенд
                proxy_pass http://IP_STAGING_VM:8080; # Укажите IP и порт вашей Staging VM с приложением
                proxy_set_header Host \$host; # Пробрасываем заголовок Host
                proxy_set_header X-Real-IP \$remote_addr; # Пробрасываем реальный IP клиента
                proxy_set_header X-Forwarded-For \$proxy_add_x_forwarded_for; # Пробрасываем цепочку прокси
                proxy_set_header X-Forwarded-Proto \$scheme; # Пробрасываем протокол (http/https)
            }

            # Опционально: обработка статических файлов
            # location /static/ {
            #    alias /path/to/static/files/; # Путь к статическим файлам на Nginx VM
            # }

            error_log /var/log/nginx/my-app-error.log;
            access_log /var/log/nginx/my-app-access.log;
        }
        ```
        *   Замените `ВАШ_IP_VM_NGINX или ВАШ_ДОМЕН` на IP или домен Nginx VM.
        *   Замените `IP_STAGING_VM` на IP адрес Staging VM, где запущено приложение в Docker контейнере (или `localhost`, если Nginx и контейнер на одной VM).

    4.  **Активируйте конфигурацию:**
        ```bash
        # На Nginx VM
        sudo ln -s /etc/nginx/sites-available/my-app.conf /etc/nginx/sites-enabled/
        # Удалите конфигурацию по умолчанию, если она мешает
        # sudo rm /etc/nginx/sites-enabled/default
        ```

    5.  **Проверьте синтаксис конфигурации Nginx:**
        ```bash
        sudo nginx -t
        ```
        Если есть ошибки, исправьте их.

    6.  **Перезагрузите Nginx для применения новой конфигурации:**
        ```bash
        sudo systemctl reload nginx # Или restart
        ```

    7.  **Проверьте доступ к приложению через Nginx:** Откройте браузер и перейдите по IP или домену Nginx VM. Вы должны увидеть ваше приложение. Логи запросов будут видны в файле `access_log`, указанном в конфигурации Nginx.

**Результат Lab 3:** Nginx настроен как Reverse Proxy, перенаправляющий входящий трафик на ваш контейнер с приложением.

**Lab 4: Настройка Nginx как Load Balancer**

*   **Цель:** Запустить несколько экземпляров приложения и настроить Nginx для распределения нагрузки между ними.
*   **Предварительные требования:**
    *   Работающий Nginx (Lab 2).
    *   Ваше приложение упаковано в Docker образ.
    *   Возможность запустить несколько экземпляров контейнера приложения на разных портах *на той же VM*, или на разных VM.
*   **Шаги:**

    1.  **Запустите несколько экземпляров контейнера приложения:**
        *   На той же Staging VM, где установлен Docker, запустите несколько контейнеров, пробрасывая их на разные порты хоста:
            ```bash
            docker run -d -p 8081:8080 --name my-app-container-1 ВАШ_IP_VM_NEXUS:8082/my-java-app:1.0.0-SNAPSHOT
            docker run -d -p 8082:8080 --name my-app-container-2 ВАШ_IP_VM_NEXUS:8082/my-java-app:1.0.0-SNAPSHOT
            docker run -d -p 8083:8080 --name my-app-container-3 ВАШ_IP_VM_NEXUS:8082/my-java-app:1.0.0-SNAPSHOT
            ```
            Теперь у вас 3 экземпляра приложения, доступные на Staging VM по портам 8081, 8082, 8083.
        *   *Примечание:* Если у вас несколько Staging VM, вы можете запустить по одному экземпляру на каждой VM на стандартном порту 8080.

    2.  **Отредактируйте файл конфигурации Nginx (`/etc/nginx/sites-available/my-app.conf`):** Добавьте блок `upstream` для определения пула серверов бэкенда и измените `proxy_pass`.

        ```nginx
        # /etc/nginx/sites-available/my-app.conf

        # Определяем пул серверов бэкенда
        upstream myapp_backend {
            # Укажите IP и порты всех экземпляров вашего приложения
            server IP_STAGING_VM:8081; # Пример: экземпляр на Staging VM, порт 8081
            server IP_STAGING_VM:8082; # Пример: экземпляр на Staging VM, порт 8082
            server IP_STAGING_VM:8083; # Пример: экземпляр на Staging VM, порт 8083
            # Если у вас несколько Staging VM:
            # server IP_STAGING_VM_1:8080;
            # server IP_STAGING_VM_2:8080;

            # Алгоритм балансировки (по умолчанию round robin)
            # least_conn; # Использовать алгоритм наименьшего количества соединений
            # ip_hash; # Использовать IP клиента для привязки к серверу
        }

        server {
            listen 80;
            server_name ВАШ_IP_VM_NGINX или ВАШ_ДОМЕН;

            location / {
                # Перенаправляем запросы на определенный пул бэкендов
                proxy_pass http://myapp_backend; # Используем имя upstream блока
                # ... (остальные proxy_set_header) ...
            }

            # ... (логи) ...
        }
        ```
        *   Замените `IP_STAGING_VM` на IP вашей Staging VM.
        *   Раскомментируйте другие алгоритмы балансировки (`least_conn`, `ip_hash`), чтобы попробовать их.

    3.  **Проверьте синтаксис Nginx и перезагрузите:**
        ```bash
        sudo nginx -t
        sudo systemctl reload nginx
        ```

    4.  **Проверьте балансировку нагрузки:**
        *   Отправьте несколько запросов к Nginx (по его IP или домену).
        *   Посмотрите логи доступа (`access_log`) на Staging VM для каждого контейнера (или просто логи контейнеров `docker logs my-app-container-1`). Вы должны увидеть, что запросы распределяются между разными экземплярами.
        *   *Опционально:* Если ваше приложение может отдавать hostname контейнера или какой-то уникальный идентификатор, это поможет визуально проверить, на какой экземпляр попал запрос.

**Результат Lab 4:** Nginx настроен как Load Balancer, распределяющий трафик между несколькими экземплярами вашего приложения, повышая его доступность и пропускную способность.

**Lab 5: Настройка Nginx для Кеширования**

*   **Цель:** Настроить Nginx для кеширования ответов вашего приложения для ускорения доставки контента и снижения нагрузки на бэкенд.
*   **Предварительные требования:**
    *   Работающий Nginx (Lab 2).
    *   Работающее приложение (можно использовать один экземпляр, не обязательно Load Balancer).
    *   Убедитесь, что ваше приложение генерирует ответы, которые подходят для кеширования (т.е. ответы на одинаковые запросы должны быть одинаковыми, не содержать пользовательских данных). Установите правильные заголовки HTTP кеширования (`Cache-Control`, `Expires`).
*   **Шаги:**

    1.  **Отредактируйте файл конфигурации Nginx (`/etc/nginx/sites-available/my-app.conf` или `/etc/nginx/nginx.conf`):**
        *   Определите зону кеша вне блока `server` (например, в блоке `http` в `/etc/nginx/nginx.conf` или в начале `my-app.conf`, если он включается в `http`).
        *   Добавьте директивы кеширования в блок `location`.

        ```nginx
        # /etc/nginx/nginx.conf (или в начале my-app.conf)
        http {
            # ... другие настройки http ...

            # Определяем зону кеша
            # myapp_cache: имя зоны
            # levels: иерархия каталогов для хранения кеша
            # keys_zone: имя зоны и объем памяти для хранения метаданных кеша (ключей)
            # max_size: максимальный размер дискового пространства для кеша
            # inactive: как долго хранить неактивные элементы кеша
            # use_temp_path=off: сохранять кеш в том же каталоге, а не во временном
            proxy_cache_path /var/cache/nginx/myapp_cache levels=1:2 keys_zone=myapp_cache:10m max_size=1g inactive=60m use_temp_path=off;

            server {
                # ... (listen, server_name, upstream) ...

                location / {
                    proxy_pass http://myapp_backend; # Или IP_STAGING_VM:8080
                    # ... (proxy_set_header) ...

                    # Включаем кеширование для этого location
                    proxy_cache myapp_cache; # Имя зоны кеша
                    # Ключ кеша (что использовать для идентификации уникального ответа). Обычно по URL.
                    proxy_cache_key "\$scheme\$request_method\$host\$request_uri\$is_args\$args";
                    # Коды ответов, которые кешировать
                    proxy_cache_valid 200 302 10m; # Кешировать ответы 200 и 302 на 10 минут
                    proxy_cache_valid 404 1m; # Кешировать ответы 404 на 1 минуту
                    # Как долго использовать кешированный ответ при ошибке или медленном бэкенде
                    proxy_cache_use_stale error timeout updating http_500 http_502 http_503 http_504;
                    # Добавить заголовок в ответ, чтобы видеть, использовался ли кеш
                    add_header X-Proxy-Cache \$upstream_cache_status;
                }
                # ... (логи) ...
            }
            # ... другие server блоки ...
        }
        ```
        *   **Важно:** Убедитесь, что каталог для кеша `/var/cache/nginx/myapp_cache` существует и у пользователя Nginx (обычно `www-data` или `nginx`) есть права на запись. Создайте его, если нужно:
            ```bash
            sudo mkdir -p /var/cache/nginx/myapp_cache
            sudo chown -R www-data:www-data /var/cache/nginx/myapp_cache # Или nginx:nginx
            ```

    2.  **Проверьте синтаксис Nginx и перезагрузите:**
        ```bash
        sudo nginx -t
        sudo systemctl reload nginx
        ```

    3.  **Проверьте работу кеширования:**
        *   Отправьте запрос к Nginx по адресу, который должен кешироваться (например, главная страница или статический API endpoint).
        *   Отправьте тот же запрос еще раз.
        *   Посмотрите заголовки ответа (например, с помощью `curl -I ВАШ_IP_VM_NGINX` или в инструментах разработчика браузера). Вы должны увидеть заголовок `X-Proxy-Cache`.
            *   `MISS`: Ответ не был в кеше, Nginx обратился к бэкенду.
            *   `HIT`: Ответ был получен из кеша Nginx.
            *   `EXPIRED`: Кеш просрочен, Nginx обратился к бэкенду.
            *   `STALE`: Nginx отдал просроченный кеш, пока обновляет его от бэкенда.
        *   Посмотрите логи доступа Nginx и логи вашего приложения. При `HIT` запросе не должно быть записи о запросе в логах приложения, только в логах Nginx.

**Результат Lab 5:** Nginx настроен для кеширования ответов от вашего приложения, что демонстрирует, как можно улучшить производительность и снизить нагрузку на бэкенд.

**Lab 6: Масштабирование с Docker Compose и Балансировщиком**

*   **Цель:** Продемонстрировать, как легко масштабировать сервисы с Docker Compose и как балансировщик автоматически начнет распределять нагрузку на новые экземпляры.
*   **Предварительные требования:**
    *   Настроенный Nginx Load Balancer (Lab 4).
    *   Ваше приложение описано в `docker-compose.yml` (Lab 1).
    *   Запущенный compose с одним экземпляром приложения.
*   **Шаги:**

    1.  **Запустите ваше приложение с Docker Compose (если оно не запущено) с одним экземпляром:**
        ```bash
        cd $HOME/my-composed-app
        docker-compose up -d --scale app=1 # Явно указываем 1 экземпляр
        ```

    2.  **Настройте Nginx Load Balancer для обращения к контейнерам, запущенным с Docker Compose:** По умолчанию Docker Compose создает свою сеть. Контейнеры в этой сети доступны друг другу по имени сервиса. Если Nginx запущен на той же VM, но *не в той же сети Docker Compose*, ему нужен будет доступ по IP VM и проброшенному порту (как в Lab 4). **Если Nginx запущен в той же сети Docker Compose (например, как отдельный сервис в том же `docker-compose.yml`), он сможет обращаться к сервисам по их именам.**

        *   **Вариант А (Nginx вне сети Compose, обращается по портам):** В этом случае `docker-compose.yml` должен пробрасывать порты всех экземпляров, и Nginx config должен их все перечислять. Это менее гибко для масштабирования.
        *   **Вариант Б (Nginx внутри сети Compose, обращается по именам сервисов):**
            *   Добавьте Nginx как сервис в ваш `docker-compose.yml`:
                ```yaml
                version: "3.8"

                services:
                  # ... (app, db, mongodb, vault-server services) ...

                  nginx:
                    container_name: my-nginx-lb
                    image: nginx:latest # Используйте официальный образ Nginx
                    ports:
                      - "80:80" # Проброс внешнего порта на Nginx
                      # - "443:443" # Для HTTPS
                    volumes:
                      # Смонтировать ваш конфиг Nginx в контейнер
                      - ./nginx.conf:/etc/nginx/nginx.conf:ro # Копируем один конфиг файл
                      # Или смонтировать каталог sites-enabled
                      # - ./nginx_sites:/etc/nginx/conf.d/:ro # Или sites-available/sites-enabled
                    depends_on:
                      - app # Nginx зависит от сервиса приложения

                volumes:
                  # ...
                # networks: # Используется сеть по умолчанию, созданная compose, или кастомная
                #  myapp-network:
                ```
            *   Напишите упрощенный Nginx конфиг, который обращается к имени сервиса `app`:
                ```nginx
                # nginx.conf (для использования с Docker Compose)
                worker_processes auto;

                events {
                    worker_connections 1024;
                }

                http {
                    include       /etc/nginx/mime.types;
                    default_type  application/octet-stream;

                    log_format  main  '\$remote_addr - \$remote_user [\$time_local] "\$request" '
                                      '\$status \$body_bytes_sent "\$http_referer" '
                                      '"\$http_user_agent" "\$http_x_forwarded_for"';

                    access_log  /var/log/nginx/access.log  main;
                    error_log /var/log/nginx/error.log;

                    sendfile        on;
                    keepalive_timeout  65;

                    # Определяем пул серверов бэкенда по имени сервиса Docker Compose!
                    # Docker Compose Service Discovery позволяет обращаться по имени сервиса 'app'
                    # Nginx сможет балансировать между всеми экземплярами сервиса 'app',
                    # запущенными с помощью docker-compose scale
                    upstream myapp_backend {
                        server app:8080; # Используем имя сервиса 'app' и внутренний порт контейнера (8080)
                        # Добавьте другие параметры балансировки/healthchecks если нужно
                        # least_conn;
                        # healthcheck; # Requires commercial Nginx or third-party module
                    }

                    server {
                        listen 80;
                        server_name localhost ВАШ_IP_VM_COMPOSE; # Или домен

                        location / {
                            proxy_pass http://myapp_backend; # Обращаемся к upstream
                            proxy_set_header Host \$host;
                            proxy_set_header X-Real-IP \$remote_addr;
                            proxy_set_header X-Forwarded-For \$proxy_add_x_forwarded_for;
                            proxy_set_header X-Forwarded-Proto \$scheme;
                        }
                    }
                }
                ```
            *   Создайте каталог `nginx_sites` или файл `nginx.conf` рядом с `docker-compose.yml` и скопируйте туда ваш конфиг.

    3.  **Масштабируйте сервис `app` с помощью Docker Compose:**
        ```bash
        docker-compose up -d --scale app=5 # Запустить 5 экземпляров сервиса 'app'
        ```
        Docker Compose создаст новые контейнеры сервиса `app`.

    4.  **Проверьте запущенные контейнеры:**
        ```bash
        docker-compose ps
        ```
        Вы должны увидеть 5 контейнеров с именами типа `my-composed-app_app_1`, `my-composed-app_app_2` и т.д.

    5.  **Проверьте балансировку на новых экземплярах:**
        *   Отправьте запросы к Nginx (по IP VM и порту 80).
        *   Если вы использовали Вариант Б (Nginx в той же сети Compose), Nginx должен автоматически обнаружить новые экземпляры сервиса `app` и начать распределять трафик между всеми 5 контейнерами (при использовании алгоритма Round Robin).
        *   Посмотрите логи контейнеров `app` или логи Nginx, чтобы убедиться в распределении трафика.

    6.  **Уменьшите количество экземпляров:**
        ```bash
        docker-compose up -d --scale app=2 # Уменьшить до 2 экземпляров
        ```
        Docker Compose остановит и удалит лишние контейнеры.

**Результат Lab 6:** Вы научились легко масштабировать многокомпонентное приложение с помощью Docker Compose и увидели, как балансировщик (Nginx) может автоматически адаптироваться к изменениям количества экземпляров сервисов (при правильной конфигурации и Service Discovery).
