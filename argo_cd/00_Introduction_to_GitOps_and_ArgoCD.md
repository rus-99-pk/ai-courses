# 00 - Введение в GitOps и ArgoCD

### Цель урока
Понять, что такое GitOps, какие проблемы он решает, и какое место в этой методологии занимает ArgoCD.

### Какую проблему решаем?
Традиционное управление Kubernetes-кластерами часто включает в себя ручные действия (`kubectl apply -f ...`), запуск скриптов с локальных машин или использование сложных CI/CD-пайплайнов, которые напрямую взаимодействуют с API Kubernetes.

**Это приводит к проблемам:**
1.  **"Дрейф конфигурации"**: Состояние кластера отличается от того, что описано в конфигурационных файлах (например, кто-то вручную внес изменения командой `kubectl edit`).
2.  **Непрозрачность**: Сложно понять, *кто*, *когда* и *почему* внес изменения в кластер. Нет единого источника правды.
3.  **Сложность отката**: Если новая версия приложения вызывает проблемы, откат к предыдущей стабильной версии может быть сложным и рискованным.
4.  **Безопасность**: Предоставление прямого доступа к Kubernetes API из CI/CD систем увеличивает поверхность атаки.

### Теория: Что такое GitOps?

**GitOps** — это операционная модель для облачных приложений, которая использует Git в качестве **единственного источника правды** (Single Source of Truth) для декларативной инфраструктуры и приложений.

Ключевые принципы GitOps:
1.  **Декларативность**: Вся система должна быть описана декларативно. Для Kubernetes это наши любимые YAML-манифесты.
2.  **Версионирование в Git**: Желаемое состояние системы хранится в Git-репозитории, что дает нам версионирование, историю изменений и возможность совместной работы через Pull/Merge Request'ы.
3.  **Автоматическое применение изменений**: Изменения в Git-репозитории автоматически применяются в кластере.
4.  **Непрерывная сверка**: Специальный агент (оператор) в кластере постоянно следит за тем, чтобы реальное состояние соответствовало желаемому (описанному в Git). Если обнаруживается расхождение, он либо исправляет его, либо уведомляет об этом.

### Роль ArgoCD

**ArgoCD** — это тот самый агент (оператор), который реализует принципы GitOps для Kubernetes.

**Как он работает:**
1.  ArgoCD устанавливается в ваш кластер.
2.  Вы "говорите" ArgoCD: "Следи за этим Git-репозиторием, за этой веткой и этой папкой".
3.  ArgoCD постоянно сравнивает YAML-манифесты из указанной папки в Git с тем, что реально запущено в кластере.
4.  Если есть разница (например, в Git новая версия `Deployment`, а в кластере старая), ArgoCD помечает приложение как `OutOfSync`.
5.  В зависимости от настроек, ArgoCD может автоматически **синхронизировать** состояние — то есть применить изменения из Git в кластер, чтобы привести его в соответствие.

![ArgoCD Workflow](https://argo-cd.readthedocs.io/en/stable/assets/argocd-architecture.png)

Таким образом, ArgoCD решает все перечисленные выше проблемы:
-   **Источник правды** — это Git.
-   **История изменений** — это `git log`.
-   **Аудит и ревью** — это Pull Requests.
-   **Откат** — это `git revert`.
-   **Безопасность** — CI-системе больше не нужен доступ к Kubernetes API. Она только собирает образ и обновляет YAML в Git. Всю "грязную" работу делает ArgoCD, который уже находится внутри кластера.
