# 08 - Лучшие практики и полезные советы

### Цель урока
Систематизировать полученные знания и рассмотреть лучшие подходы к структурированию репозиториев, использованию продвинутых функций и обеспечению безопасности и производительности при работе с ArgoCD в production.

### Какую проблему решаем?
Начав работать с ArgoCD, легко увлечься и создать хаос: смешать код приложения с конфигурацией, раздать всем права администратора, создать сотни почти одинаковых `Application`. Этот урок поможет выстроить масштабируемую и поддерживаемую архитектуру.

### 1. Структура Git-репозиториев

Существует два основных подхода к организации репозиториев для GitOps.

#### Подход 1: Один репозиторий для всего (Monorepo)
*   **Что это:** Код всех приложений и все Kubernetes-манифесты находятся в одном большом Git-репозитории.
*   **Структура:**
    ```
    monorepo/
    ├── services/
    │   ├── service-a/
    │   │   ├── src/
    │   │   └── Dockerfile
    │   └── service-b/
    │       ├── src/
    │       └── Dockerfile
    └── deploy/
        ├── staging/
        │   ├── service-a.yaml
        │   └── service-b.yaml
        └── prod/
            ├── service-a.yaml
            └── service-b.yaml
    ```
*   **Плюсы:**
    *   Все в одном месте, атомарные коммиты (изменение кода и деплоя одновременно).
    *   Проще настроить CI/CD.
*   **Минусы:**
    *   Сложнее управлять правами доступа (все видят всё).
    *   Репозиторий может стать очень большим и медленным.
*   **Когда использовать:** Для небольших команд или проектов, где все разработчики имеют схожий уровень доступа и контекста.

#### Подход 2: Отдельные репозитории (Multi-repo) - **РЕКОМЕНДУЕТСЯ**
*   **Что это:** У вас есть отдельные репозитории для кода каждого приложения и один или несколько репозиториев для Kubernetes-конфигураций.
*   **Структура:**
    *   `app-service-a-repo` (код)
    *   `app-service-b-repo` (код)
    *   `k8s-configs-repo` (конфигурации)
        ```
        k8s-configs-repo/
        ├── apps/
        │   ├── service-a/
        │   │   └── all-manifests.yaml
        │   └── service-b/
        │       └── all-manifests.yaml
        └── clusters/
            ├── staging/
            │   └── root-app-of-apps.yaml
            └── prod/
                └── root-app-of-apps.yaml
        ```
*   **Плюсы:**
    *   **Четкое разделение ответственности**: Разработчики работают в репозиториях приложений, DevOps-инженеры — в репозитории конфигураций.
    *   **Безопасность**: Можно гранулярно настраивать права доступа. CI-системе нужны права на запись только в конфигурационный репозиторий.
    *   **Масштабируемость**: Легко управлять сотнями приложений.
*   **Минусы:**
    *   Требуется настройка взаимодействия между репозиториями (например, CI из репо приложения должен триггерить обновление в репо конфигураций).
*   **Когда использовать:** Почти всегда. Это наиболее масштабируемый, безопасный и общепринятый подход.

### 2. Паттерн "App of Apps" (Приложение из приложений)

Не создавайте `Application` для каждого микросервиса вручную. Используйте паттерн "App of Apps" или, что еще лучше, `ApplicationSet`.

**Идея:** У вас есть одно корневое `Application`, которое разворачивает другие `Application`. Это позволяет управлять всем окружением (dev, staging, prod) как единым целым.

**Пример (App of Apps):**
`root-app-staging.yaml`:
```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: staging-environment
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/my-org/k8s-configs-repo.git
    targetRevision: HEAD
    # Эта папка содержит YAML-файлы для всех приложений стейджинга
    path: apps/staging
  destination:
    server: https://kubernetes.default.svc
    namespace: argocd
```
В папке `apps/staging` лежат `app-1.yaml`, `app-2.yaml` и т.д.

**Почему `ApplicationSet` лучше:**
`ApplicationSet` является развитием этого паттерна. Он более декларативен и гибок благодаря генераторам. Используйте генератор `Git` (directory) для автоматического обнаружения и развертывания новых приложений. Это избавляет от необходимости вручную добавлять новый `application.yaml` в папку.

### 3. Используйте Kustomize или Helm

Не храните "сырые" YAML-манифесты. Используйте инструменты для шаблонизации, чтобы управлять различиями между окружениями (dev, staging, prod).

*   **Kustomize:** Отлично подходит для управления небольшими различиями (количество реплик, URL, ресурсы CPU/Memory). Интегрирован в `kubectl` и нативно поддерживается ArgoCD.
    *   **Структура:**
        ```
        app/
        ├── base/
        │   ├── deployment.yaml
        │   └── kustomization.yaml
        └── overlays/
            ├── staging/
            │   ├── replicas.yaml
            │   └── kustomization.yaml
            └── prod/
                ├── replicas.yaml
                └── kustomization.yaml
        ```
    ArgoCD `Application` будет указывать на `overlays/staging` или `overlays/prod`.

*   **Helm:** Мощный пакетный менеджер для Kubernetes. Идеален для распространения и переиспользования сложных приложений (например, Prometheus, GitLab). ArgoCD имеет отличную поддержку Helm, включая передачу `values.yaml`.

**Совет:** Не смешивайте Kustomize и Helm для одного приложения. Выберите один инструмент.

### 4. Безопасность — ваш приоритет

*   **Не используйте проект `default`:** Создавайте `AppProject` для каждой команды или группы приложений. Ограничивайте `sourceRepos`, `destinations` и `clusterResourceWhitelist/Blacklist`, чтобы предотвратить несанкционированный доступ.
*   **Минимизируйте права доступа:** Настройте RBAC в ArgoCD. Давайте пользователям и CI-системам только те права, которые им действительно нужны. Не используйте токен `admin` в скриптах.
*   **Используйте `Sealed Secrets` или `External Secrets Operator`:** Никогда не храните секреты в Git в открытом виде.
*   **Включайте `selfHeal` и `prune`:** Для автоматизированных окружений это must-have для борьбы с дрейфом конфигурации и "мусорными" ресурсами.
*   **Регулярно обновляйте ArgoCD:** Как и любое ПО, ArgoCD имеет уязвимости. Следите за новыми релизами и патчами безопасности.

### 5. Оптимизация производительности

Когда у вас тысячи приложений, ArgoCD может начать потреблять много ресурсов.

*   **Увеличьте количество реплик `argocd-repo-server`:** Этот компонент отвечает за клонирование Git-репозиториев и рендеринг манифестов. Если у вас много приложений, он может стать узким местом.
    ```bash
    kubectl scale deployment argocd-repo-server -n argocd --replicas=3
    ```
*   **Настройте кэширование:** `argocd-repo-server` кэширует Git-репозитории. Убедитесь, что у него достаточно дискового пространства. Можно настроить время жизни кэша.
*   **Используйте Webhooks вместо поллинга:** По умолчанию ArgoCD опрашивает Git-репозитории каждые 3 минуты. Это создает нагрузку и задержку. Настройте Git Webhook (в GitHub/GitLab), чтобы Git сам уведомлял ArgoCD о новых коммитах. Это мгновенно и эффективно.
