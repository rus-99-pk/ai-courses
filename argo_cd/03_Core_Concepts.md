# 03 - Ключевые концепции ArgoCD

### Цель урока
Разобраться в фундаментальных понятиях ArgoCD: политиках синхронизации, статусах здоровья, проектах и волнах синхронизации. Понимание этих концепций необходимо для эффективного управления приложениями в production.

### Какую проблему решаем?
На прошлом шаге мы вручную нажимали кнопку SYNC. Но что если мы хотим, чтобы все происходило автоматически? Что если один из наших подов упадет после развертывания — как ArgoCD это поймет? Как ограничить права команды, чтобы она могла разворачивать приложения только в свой неймспейс? Как управлять зависимостями, когда один ресурс должен быть создан раньше другого?

На все эти вопросы отвечают ключевые концепции ArgoCD.

### 1. Политики синхронизации (Sync Policies)

Политика синхронизации определяет, *как* и *когда* ArgoCD применяет изменения из Git в кластер.

#### Manual Sync (Ручная синхронизация)
Это поведение по умолчанию, которое мы использовали ранее.
*   **Как работает:** ArgoCD обнаруживает расхождение (`OutOfSync`), но ничего не делает. Оператор должен вручную нажать кнопку `SYNC`.
*   **Когда использовать:** В критически важных окружениях (production), где любое изменение требует явного одобрения.

#### Automated Sync (Автоматическая синхронизация)
Это "сердце" GitOps.
*   **Как работает:** Как только ArgoCD обнаруживает, что состояние в Git отличается от состояния в кластере, он немедленно запускает синхронизацию.
*   **Когда использовать:** В окружениях для разработки (dev) и тестирования (staging), чтобы разработчики мгновенно видели свои изменения. Также используется в production при зрелых процессах CI/CD и ревью через Pull Request'ы.

**Дополнительные опции автоматической синхронизации:**
*   **Prune Resources (Очистка ресурсов):** Если вы удалили YAML-файл из Git-репозитория, ArgoCD с этой опцией удалит соответствующий ресурс из кластера. **Крайне рекомендуется включать**, чтобы в кластере не оставалось "мусорных" ресурсов.
*   **Self Heal (Самовосстановление):** Если кто-то вручную изменит ресурс в кластере (например, через `kubectl edit`), ArgoCD обнаружит это расхождение и автоматически вернет ресурс к состоянию, описанному в Git. Это защищает от "дрейфа конфигурации".

**Пример манифеста Application с автоматической синхронизацией:**
```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: guestbook
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/argoproj/argocd-example-apps.git
    targetRevision: HEAD
    path: guestbook
  destination:
    server: https://kubernetes.default.svc
    namespace: guestbook
  
  # Вот наша политика синхронизации
  syncPolicy:
    automated:
      prune: true      # Включаем удаление старых ресурсов
      selfHeal: true   # Включаем самовосстановление
```

### 2. Статусы здоровья (Health Status)

ArgoCD не просто применяет манифесты. Он анализирует состояние созданных ресурсов, чтобы понять, действительно ли приложение работает.

*   **OutOfSync**: Состояние в Git не соответствует состоянию в кластере.
*   **Synced**: Состояние в кластере соответствует Git.
*   **Healthy**: Все ресурсы приложения находятся в "здоровом" состоянии (например, `Deployment` имеет нужное количество готовых реплик, `Pod` находится в статусе `Running`).
*   **Progressing**: Приложение находится в процессе развертывания. Например, `Deployment` выполняет rolling update, и старые поды еще не заменены новыми.
*   **Degraded**: Один или несколько ресурсов находятся в нерабочем состоянии (например, `Pod` в статусе `CrashLoopBackOff` или `ImagePullBackOff`). Это сигнал, что что-то пошло не так.
*   **Suspended**: Развертывание ресурса приостановлено. Например, `CronJob` с флагом `suspend: true`.
*   **Missing**: Ресурс определен в Git, но отсутствует в кластере.

ArgoCD "знает" о стандартных ресурсах Kubernetes. Для ваших собственных Custom Resources (CRD) можно написать кастомные проверки здоровья на Lua.

### 3. Проекты (Projects)

Проекты — это инструмент для группировки приложений и управления доступом (RBAC). Проект `default`, который мы использовали, разрешает всё и всем. В реальном мире это небезопасно.

Проекты позволяют ограничить:
*   **Откуда** можно разворачивать приложения (список разрешенных Git-репозиториев).
*   **Куда** можно разворачивать приложения (список разрешенных кластеров и неймспейсов).
*   **Что** можно разворачивать (список разрешенных или запрещенных типов ресурсов, например, запретить создание `ClusterRole`).
*   **Кто** имеет доступ (интеграция с группами пользователей для предоставления прав на просмотр, синхронизацию и т.д.).

**Пример манифеста AppProject:**
Представим, что у нас есть команда "alpha", которая может деплоить только в неймспейс `alpha-ns` из своего репозитория.

```yaml
apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: team-alpha-project
  namespace: argocd
spec:
  description: Project for Team Alpha

  # Разрешаем развертывание только из этого репозитория
  sourceRepos:
  - 'https://github.com/my-org/team-alpha-app.git'

  # Разрешаем развертывание только в этот кластер и в этот неймспейс
  destinations:
  - namespace: alpha-ns
    server: 'https://kubernetes.default.svc'

  # Запрещаем создание ресурсов, которые влияют на весь кластер
  clusterResourceWhitelist:
  - group: ''
    kind: Namespace
  namespaceResourceBlacklist:
  - group: '*'
    kind: '*'
```
После создания этого проекта, при создании `Application` можно будет указать `project: team-alpha-project`.

### 4. Волны синхронизации и хуки (Sync Waves & Hooks)

Иногда порядок создания ресурсов важен. Например, `Secret` с паролем от базы данных должен быть создан *до* того, как запустится `Deployment`, который этот пароль использует.

#### Sync Waves
ArgoCD позволяет управлять порядком синхронизации с помощью аннотации `argocd.argoproj.io/sync-wave`.

*   Ресурсы с меньшим номером волны синхронизируются раньше.
*   Ресурсы без аннотации находятся в волне `0`.
*   Можно использовать отрицательные числа (например, для создания `Namespace` или `CRD`).
*   ArgoCD ждет, пока все ресурсы в текущей волне станут `Healthy`, прежде чем перейти к следующей.

**Пример:** Сначала создаем PVC, потом — Pod, который его использует.
```yaml
# pvc.yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: my-pvc
  annotations:
    argocd.argoproj.io/sync-wave: "-5"
spec:
  # ...
---
# pod.yaml
apiVersion: v1
kind: Pod
metadata:
  name: my-pod
  annotations:
    argocd.argoproj.io/sync-wave: "5"
spec:
  # ...
```

#### Sync Hooks
Хуки позволяют выполнять задачи (обычно `Job` или `Pod`) в определенные моменты жизненного цикла синхронизации.

*   `PreSync`: Выполняется до начала синхронизации. Пример: создание бэкапа базы данных.
*   `Sync`: Выполняется во время синхронизации, параллельно с другими ресурсами.
*   `PostSync`: Выполняется после того, как все ресурсы стали `Healthy`. Пример: запуск миграции базы данных, прогон тестов.
*   `SyncFail`: Выполняется, если синхронизация завершилась с ошибкой. Пример: отправка уведомления, откат бэкапа.

**Пример:** `Job` для миграции БД после успешного развертывания.
```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: db-migration
  annotations:
    # Этот Job будет запущен после того, как все остальные ресурсы станут Healthy
    argocd.argoproj.io/hook: PostSync
    # Удалить Job после успешного выполнения, чтобы не засорять кластер
    argocd.argoproj.io/hook-delete-policy: HookSucceeded
spec:
  template:
    spec:
      containers:
      - name: migration-container
        image: my-app-migrator:v1.2
      restartPolicy: Never
  backoffLimit: 2
```

Теперь вы знаете о "рычагах управления", которые предоставляет ArgoCD. В следующем уроке мы рассмотрим, как управлять не одним, а десятками однотипных приложений с помощью `ApplicationSet`.
