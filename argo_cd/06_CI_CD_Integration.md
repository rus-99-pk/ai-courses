# 06 - Интеграция с CI/CD: Обновление образов

### Цель урока
Понять, как соединить процесс непрерывной интеграции (CI), где собираются и пушатся Docker-образы, с процессом непрерывного развертывания (CD), управляемым ArgoCD.

### Какую проблему решаем?
Сейчас наш Git-репозиторий с Kubernetes-манифестами (будем называть его **конфигурационный репозиторий**) содержит фиксированную версию Docker-образа, например:

`deployment.yaml`:
```yaml
...
spec:
  template:
    spec:
      containers:
      - name: my-app
        image: my-company/my-app:1.0.0 # Жестко заданный тег
...
```

Когда разработчик вносит изменения в код приложения (в **репозитории приложения**), CI-система (например, GitHub Actions, GitLab CI, Jenkins) собирает новый Docker-образ и пушит его в registry с новым тегом (например, `my-company/my-app:1.1.0` или `my-company/my-app:git-commit-sha`).

**Вопрос:** Как сообщить ArgoCD, что нужно использовать этот новый тег?

**Неправильный подход:** Давать CI-системе прямой доступ к Kubernetes API для выполнения `kubectl set image ...`. Это нарушает главный принцип GitOps: Git — единственный источник правды.

**Правильный подход:** CI-система должна **обновить YAML-файл в конфигурационном репозитории**. ArgoCD увидит это изменение и автоматически (или вручную) синхронизирует приложение.

### Паттерны обновления тега в Git

Существует несколько стратегий, как CI-пайплайн может обновлять тег образа в конфигурационном репозитории.

#### Паттерн 1: Прямой коммит в ветку (для Dev-окружений)

Самый простой способ, подходящий для сред разработки.

**Сценарий:**
1.  Разработчик пушит код в `main` ветку репозитория приложения.
2.  CI-пайплайн запускается:
    a. Собирает Docker-образ и тегирует его (например, хешем коммита `sha-1234567`).
    b. Пушит образ в Docker Registry: `my-company/my-app:sha-1234567`.
    c. Клонирует **конфигурационный репозиторий**.
    d. Находит нужный `deployment.yaml` и обновляет поле `image` на новый тег.
    e. Коммитит и пушит изменения напрямую в `main` ветку конфигурационного репозитория.
3.  ArgoCD, настроенный на автоматическую синхронизацию (`automated sync`), видит новый коммит и разворачивает приложение с новым образом.

**Пример шага в GitHub Actions:**
```yaml
      - name: Update Kubernetes manifest
        run: |
          git clone https://x-access-token:${{ secrets.GIT_TOKEN }}@github.com/my-org/my-k8s-configs.git
          cd my-k8s-configs
          # Используем yq, kustomize или просто sed для обновления
          sed -i "s|image: my-company/my-app:.*|image: my-company/my-app:${{ steps.docker_build.outputs.digest }}|" ./apps/my-app/deployment.yaml
          git config user.name "GitHub Actions"
          git config user.email "actions@github.com"
          git commit -am "Update image for my-app to ${{ steps.docker_build.outputs.digest }}"
          git push
```
*   **Плюсы:** Просто и быстро.
*   **Минусы:** Нет ревью изменений в конфигурации. Не подходит для `staging` и `production`.

#### Паттерн 2: Создание Pull/Merge Request (для Staging/Production)

Это более безопасный и контролируемый подход.

**Сценарий:**
1.  Разработчик пушит код.
2.  CI-пайплайн собирает и пушит образ.
3.  CI-пайплайн:
    a. Клонирует конфигурационный репозиторий.
    b. Создает новую ветку (например, `update-my-app-sha-1234567`).
    c. Обновляет тег образа в YAML.
    d. Коммитит изменения в новую ветку.
    e. **Создает Pull Request (PR)** из новой ветки в `main` (или `staging`).
4.  DevOps-инженер или тимлид делает ревью PR. Они видят, какая версия приложения будет развернута.
5.  После мержа PR в целевую ветку, ArgoCD подхватывает изменения и начинает развертывание.

*   **Плюсы:** Полный контроль и аудит. Возможность отклонить развертывание.
*   **Минусы:** Требует ручного вмешательства (мерж PR), что замедляет процесс.

### Альтернатива: Argo CD Image Updater

Что если мы не хотим давать CI-системе права на запись в наш Git-репозиторий? Для этого существует отдельный инструмент — **Argo CD Image Updater**.

**Идея:** Это небольшой контроллер, который работает рядом с ArgoCD. Вы "говорите" ему, за какими образами в Docker Registry следить. Он периодически проверяет registry на наличие новых тегов, которые соответствуют определенной стратегии (например, semver), и сам обновляет `Application` CRD, чтобы указать на новый тег.

**Как это работает:**
1.  Вы устанавливаете Image Updater в ваш кластер.
2.  Вы добавляете специальные аннотации в ваш `Application` манифест.

**Пример манифеста `Application` с аннотациями для Image Updater:**
```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: my-app
  namespace: argocd
  annotations:
    # 1. Включаем обновление для этого приложения
    argocd-image-updater.argoproj.io/image-list: myapp=my-company/my-app
    # 2. Указываем стратегию обновления. Например, следить за последним стабильным semver-тегом.
    argocd-image-updater.argoproj.io/myapp.update-strategy: semver
    # 3. Указываем, как обновлять тег в источнике (например, для Helm)
    argocd-image-updater.argoproj.io/myapp.helm.image-spec: image.tag
spec:
  source:
    repoURL: https://github.com/my-org/my-helm-charts.git
    chart: my-app
    targetRevision: 1.0.0
    helm:
      # Изначально тег может быть любым
      parameters:
      - name: "image.tag"
        value: "1.0.0"
  # ...
```

**Сценарий с Image Updater:**
1.  CI-пайплайн просто собирает и пушит образ с семантическим тегом (например, `my-company/my-app:1.2.0`). **Больше он ничего не делает с Git.**
2.  Argo CD Image Updater сканирует Docker Registry и видит новый тег `1.2.0`, который "новее", чем текущий `1.1.0`.
3.  Image Updater напрямую изменяет `Application` CRD в Kubernetes (или делает коммит в Git, если настроено), обновляя параметр `helm.parameters` на `image.tag=1.2.0`.
4.  ArgoCD видит, что `Application` изменился и стал `OutOfSync`, и запускает синхронизацию.

*   **Плюсы:** Разделение зон ответственности (CI отвечает за код, CD — за развертывание). Не нужно давать CI-системе доступ к конфигурационному репозиторию.
*   **Минусы:** Еще один компонент для установки и настройки. Меньшая гибкость по сравнению с прямым управлением через Git.

### Рекомендации

*   **Для Dev/Test:** Используйте **Паттерн 1 (прямой коммит)** или **Argo CD Image Updater** для максимальной скорости.
*   **Для Staging/Prod:** Используйте **Паттерн 2 (Pull Request)**. Это золотой стандарт GitOps, обеспечивающий безопасность и контроль.

Ключевой вывод: CI и CD — это два разных процесса. CI заканчивается на пуше артефакта (Docker-образа). CD начинается с обновления декларативной конфигурации в Git. ArgoCD — это сердце вашего CD-процесса.
