### Методичка по ДЗ: Модуль 4, Тема 6

**Название ДЗ:** Обновление версии приложения через GitOps

**Цель ДЗ:** Практически продемонстрировать основной цикл GitOps для приложений: изменение желаемого состояния в Git (обновление тега образа) и автоматическое применение этого изменения в кластере с помощью Argo CD или Flux.

**Необходимые условия/Инструменты:**

1.  Работающий кластер Kubernetes с установленным `kubectl`.
2.  Установленный Git.
3.  Аккаунт на Git-хостинге с GitOps-репозиторием, содержащим манифесты простого приложения (Deployment, Service), который синхронизируется с кластером с помощью **Argo CD** или **Flux** (после ДЗ Модуля 3, Тема 2 или Тема 4).
4.  Два разных тега одного Docker-образа, развернутого приложения, где видна разница между версиями (например, Nginx `latest` и `1.25.2`, или ваш кастомный образ с разными метками версии на веб-странице).

**Подробные шаги (Выберите инструмент, который вы использовали в Модуле 3):**

**Шаг 1: Определите приложение и его манифесты в Git**

Выберите приложение из вашего GitOps репозитория, которое уже успешно деплоится с помощью Argo CD или Flux. Найдите YAML-файл Deployment для этого приложения.

Пример: `my-gitops-apps/apps/app1/deployment.yaml` (для Nginx с Argo CD) или `my-gitops-flux/apps/my-app/app-deployment.yaml` (для Nginx с Flux).

Убедитесь, что вы знаете имя Deployment в кластере (например, `app1-nginx-deployment` или `my-nginx-app`).

**Шаг 2: Определите текущий тег образа и новый тег**

Посмотрите в манифесте Deployment в Git, какой тег образа используется сейчас (например, `nginx:latest`).

Найдите или подготовьте другой тег того же образа. Например, `nginx:1.25.2` или `nginx:1.24.0`.

Если у вас кастомное приложение, убедитесь, что у вас есть два разных тега, и вы можете как-то визуально или по логам отличить, какая версия запущена.

**Шаг 3: Измените тег образа в манифесте Deployment в Git**

Отредактируйте YAML-файл Deployment в локальной копии вашего GitOps репозитория. Измените значение поля `image` в спецификации контейнера на новый тег.

```yaml
# Ваш файл Deployment (фрагмент)
apiVersion: apps/v1
kind: Deployment
metadata:
  name: app1-nginx-deployment # Или имя вашего деплоймента
spec:
  ...
  template:
    ...
    spec:
      containers:
      - name: nginx # Имя контейнера
        image: nginx:1.25.2 # <-- ИЗМЕНИТЕ ЭТУ СТРОКУ на новый тег
        ports:
        - containerPort: 80
...
```

**Шаг 4: Добавьте, закоммитьте и отправьте изменение в Git**

Сохраните файл, добавьте изменение, создайте новый коммит и отправьте его на удаленный репозиторий.

```bash
git add <путь_к_вашему_deployment_файлу> # Например, apps/app1/deployment.yaml
git commit -m "Update app1-nginx to version 1.25.2" # Опишите изменение
git push origin main # Или master
```

*   **Проверка:** Убедитесь, что новый коммит появился в вашем удаленном Git-репозитории, и в нем изменена строка с тегом образа. Запомните или скопируйте хеш этого коммита.

**Шаг 5: Наблюдайте за синхронизацией вашего GitOps инструмента**

Ваш GitOps инструмент (Argo CD или Flux) автоматически (или после ручного триггера) увидит новый коммит в Git-репозитории. Он сравнит желаемое состояние (теперь с новым тегом образа) с фактическим состоянием в кластере. Обнаружив "дрифт" (отличие), он начнет процесс синхронизации, который в случае Deployment приведет к постепенному обновлению подов (по умолчанию используется стратегия Rolling Update).

*   **Для Argo CD:** Откройте веб-интерфейс. Найдите Application для вашего приложения. Вы увидите, что его статус перейдет в `OutOfSync`, затем начнется синхронизация, и он перейдет в `Progressing`. При синхронизации будет показано, что Deployment обновляется, и поды создаются/удаляются. Дождитесь, пока Application снова перейдет в `Synced` и `Healthy`.
*   **Для Flux CD:** Смотрите логи контроллеров Flux (`kustomize-controller` или `helm-controller`). Или используйте команды `flux get kustomizations` (или `helmreleases`) и `flux logs --follow --level=info`. Вы увидите, как Flux обнаруживает изменение в Git и начинает применять его к кластеру. Дождитесь, пока Kustomization/HelmRelease перейдет в статус `Ready`.

**Шаг 6: Проверьте, что Deployment обновлен и запущена новая версия**

Используйте `kubectl` для проверки состояния Deployment и образов запущенных подов.

```bash
# Проверьте статус Deployment
kubectl get deploy <имя_деплоймента> -n <неймспейс> # Замените имя и неймспейс

# Проверьте тег образа в спеке Deployment (желаемое состояние)
kubectl get deploy <имя_деплоймента> -n <неймспейс> -o yaml | grep image

# Проверьте тег образа в спеке запущенных подов (фактическое состояние)
kubectl get pods -l app=<лейбл_вашего_приложения> -n <неймспейс> -o yaml | grep image
```

*   **Ожидаемый результат:** `kubectl get deploy` должен показать желаемое количество реплик (`DESIRED`), а также актуальное (`CURRENT`, `UP-TO-DATE`, `AVAILABLE`) должно соответствовать желаемому. `grep image` должен показать новый тег образа как в спеке Deployment, так и в спеке запущенных подов.

**Шаг 7: Продемонстрируйте, что приложение работает с новой версией**

Получите доступ к вашему приложению (через Service NodePort, LoadBalancer или Ingress, как вы делали в ДЗ Модуля 1).

*   **Для Nginx:** Вы можете увидеть версию Nginx в заголовках ответа (curl -I) или на стандартной приветственной странице, если она включена.
    ```bash
    curl -I http://<IP:Port_вашего_приложения>
    # Ищите заголовок "Server: nginx/X.Y.Z"
    ```
    Или просто `curl http://<IP:Port>` и посмотрите содержимое страницы. У разных версий Nginx могут быть незначительные отличия.
*   **Для кастомного приложения:** Обратитесь к нему через UI или API, чтобы увидеть признак новой версии (номер версии, измененный текст и т.д.).

*   **Ожидаемый результат:** Вы должны увидеть признаки того, что запущена именно новая версия приложения (соответствующая измененному тегу образа).

**Проверка результатов (Измеряемость):**

1.  Предоставьте ссылку на ваш GitOps-репозиторий.
2.  Предоставьте ссылку на конкретный коммит в Git, где вы изменили тег образа Deployment.
3.  Предоставьте вывод команды `kubectl get deploy <имя_деплоймента> -n <неймспейс> -o yaml | grep image` (после синхронизации GitOps инструмента), показывающий, что в кластере используется новый тег образа.
4.  Предоставьте вывод команды или скриншот, демонстрирующий, что при доступе к приложению видна новая версия (например, вывод `curl -I` с заголовком Server, или скриншот веб-страницы). Укажите IP и порт/URL, который вы использовали.
5.  (Опционально) Предоставьте скриншоты из веб-интерфейса Argo CD или логи контроллеров Flux, показывающие процесс обнаружения изменения и синхронизации Deployment.
